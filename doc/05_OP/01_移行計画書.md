### Step 4: Render へのデプロイ

サイト本体は Render の Web Service で動かす。リポジトリに Render の設定ファイル（`render.yaml`）は無いので、設定は Render の画面で行う。

1. Render の Dashboard で、GitHub のリポジトリ `ei8htplants-site` をつないだ Web Service を作る（ブランチは `main`）
2. Settings で、Python のバージョン（リポジトリ直下の `.python-version` は 3.12.9）・Build Command（`backend/requirements.txt` のインストール）・Start Command（`backend` で uvicorn を起動する。例 `uvicorn app.main:app --host 0.0.0.0 --port $PORT`）を設定する。今の本番の値は Render の Settings の画面で確かめる
3. Environment に Step 2 のバックエンドの環境変数を入れる
4. Settings > Custom Domains に `ei8htplants.com` を追加し、ドメインの DNS を Render の案内どおりに設定する（HTTPS の証明書は Render が自動で用意する）
5. 以後は `main` にプッシュすると自動でデプロイされる。手で反映したいときは Render の画面の **[Manual Deploy]** を使う

> 分析ダッシュボードは Render ではなく Streamlit Community Cloud で動かす（[分析ダッシュボードの公開手順](04_分析ダッシュボードの公開手順.md)）。

## 3. サーバー移行手順（将来）

今の Render から、別の Render のサービスやほかのホスティングへ移す場合。

### データバックアップ

```bash
# Supabase管理画面 > Settings > Database > Backups から手動バックアップを取得
# または pg_dump（Supabase Direct Connection）:
pg_dump "postgresql://postgres.<project-id>:<password>@aws-0-ap-northeast-1.pooler.supabase.com:5432/postgres" > backup.sql
```

### 切り替え手順

```
1. 移行先で本番デプロイ手順（Step 2〜4。DB も移すときは Step 1 も）を実施
2. ドメインの DNS レコードを移行先の案内どおりに変更
3. 旧サーバーへのアクセスが減少したことを確認
4. 旧サーバーの停止
```

### ロールバック方針

本番切り替え後に重大な問題が発生した場合:
1. DNS を旧サーバーに戻す（TTL次第で1〜24時間）
2. 問題を修正後、再度切り替え

## 5. 個別の DB 変更手順

### 5-1. イベント管理情報を専用テーブルへ移す（016・018・017。2026-10-16 作成）

**目的**: イベントの管理情報（搬入・搬出・宿泊・出店料・出店要項など）は、これまで events テーブルの `admin_info` 列に入っていた。events テーブルはログインしていない人でも読める設定のため、Supabase に直接問い合わせると管理情報まで読めてしまっていた。ログインしていない人は読めない専用テーブル `event_admin_info` に移し、古い列を削除する。詳しいテーブルの内容は [データベース詳細](../02_DD/05_データベース詳細.md) の event_admin_info の節を参照。

**使うファイル**: `backend/migrations/016_event_admin_info.sql`、`backend/migrations/018_grant_event_admin_info.sql`、`backend/migrations/017_drop_events_admin_info.sql`（番号順ではなく、下の手順の順に実行する）

**手順**（この順番を必ず守る）:

| 順 | 作業 | 場所 | 確認すること |
|---|---|---|---|
| 1 | `016_event_admin_info.sql` の中身を貼り付けて実行する | Supabase 管理画面 > SQL Editor | エラーが出ないこと。新しいテーブルを作り、今ある管理情報を写す。古い列は残るので、この時点ではサイトも管理画面もそのまま動く。ただしこの時点では、events の `admin_info` 列に古い管理情報が残っていて、未ログインでも Supabase に直接問い合わせると読める（対策が完了するのは手順 4 の後） |
| 2 | `018_grant_event_admin_info.sql` の中身を貼り付けて実行する（手順 1 の直後、デプロイより前） | Supabase 管理画面 > SQL Editor | エラーが出ないこと。サーバーが新しいテーブルを読み書きできるようになる |
| 3 | 新しいプログラムをデプロイする（`main` へのプッシュで Render が自動で反映） | Render | デプロイ完了後、管理画面でいくつかのイベントの「管理情報」を開き、登録済みの搬入・宿泊・出店料・出店要項が表示されること |
| 4 | `017_drop_events_admin_info.sql` の中身を貼り付けて実行する | Supabase 管理画面 > SQL Editor | エラーが出ないこと。実行後にもう一度、管理画面で管理情報が表示されること。これで外から読めなくなる（この手順を必ず行う） |

**注意**:

- 手順 3 より前に手順 4 を実行しない。古いプログラムが削除済みの列を読もうとして、管理情報の表示・保存ができなくなる
- 手順 1・2 より前に手順 3 を行わない。新しいプログラムが、まだない（または権限の無い）新しいテーブルを読もうとして、管理情報の表示・保存ができなくなる
- このプロジェクトの Supabase では、新しいテーブルを作ってもサーバー（`service_role`）の権限が自動で付かない場合がある。新しいテーブルを作ったら、018 のように GRANT（権限を付ける SQL）を忘れずに実行する
- 1〜4 は、管理画面で管理情報や収支を保存しない時間帯に続けて行うのが望ましい（収支画面の保存でも管理情報（出店料・宿泊費）が書き込まれるため）。途中で保存しても、016 で入れた自動の写し（トリガー）と 017 の写し直しで内容は失われないようにしている
- 016・017 は途中で失敗すると全体が取り消される
- 016 は 017 を実行する前なら何度実行しても同じ結果になる。017 は 1 回だけ実行する（2 回目以降は失敗するが、全体が取り消されるので害はない）。018 は何度実行しても同じ結果になる

**経緯（2026-10-16）**: 最初は 018 が無く、016 の実行とデプロイの後に、サーバーが新しいテーブルを読み書きできず（`permission denied for table event_admin_info`）、管理画面の管理情報ページが「データの読み込みに失敗しました」となり一時的に読み込めなかった。018 と同じ SQL を実行して解消した

### 5-2. データベースの権限を絞る（019。2026-10-23 作成）

**目的**: 画面に公開している Supabase の鍵（anon キー）で、サーバーの API を通さずに Supabase へ直接問い合わせたときに、できてはいけないことをできなくする。

| 内容 | それまで | 019 の後 |
|---|---|---|
| ワークショップ予約 | 誰でも直接予約を書き込めた（入力の確認・満席の確認・回数制限を通らない） | 直接は書き込めない。予約は API（`POST /api/reserve`）からだけ |
| 記事 | 下書き（公開していない記事）も直接読めた | 直接読めるのは公開済みの記事だけ |
| 在庫を減らす関数 `decrement_stock` | 誰でも呼べた。0 以下の数でも動き、負の数を渡すと在庫が増えた | サーバーだけが呼べる。1 以上の数のときだけ減らす |
| 在庫を戻す関数 `increment_stock` | 誰でも呼べた | サーバーだけが呼べる（負の数の確認は無い。課題表 I-18） |

**使うファイル**: `backend/migrations/019_security_hardening.sql`

**手順**:

| 順 | 作業 | 場所 | 確認すること |
|---|---|---|---|
| 1 | `019_security_hardening.sql` の中身をすべて貼り付けて実行する | Supabase 管理画面 > SQL Editor | エラーが出ないこと |
| 2 | 公開サイトで、予約・注文・記事が今までどおり使えるかを確かめる | 公開サイト | イベントの予約ページで予約できる（テスト用のイベントで確かめ、確かめた予約は管理画面でキャンセルにする）／ショップの商品ページ・購入手続きが開ける（注文まで試すときはテスト用の商品で）／ジャーナルで公開中の記事が読める |
| 3 | 管理画面で、記事の一覧に下書きも出ること・WS予約の一覧が出ることを確かめる | 管理画面 | 今までどおり表示される |

**注意**:

- 新しいプログラムのデプロイの前に実行しても後に実行してもよい（サーバーは予約・記事・在庫の読み書きをすべてサーバー用の鍵（service_role）で行っているので、どちらの順でもサイトの動きは変わらない）
- 何度実行しても同じ結果になる。途中で失敗したときは全体が取り消されるので、原因を直してもう一度実行する
- 実行の最後に、Supabase の API に権限の変更を知らせる（`NOTIFY pgrst, 'reload schema'`）ので、すぐに反映される

### 5-3. 販売価格計算の登録リストのテーブルを作る（020。2026-10-24 作成・実行済み（2026-10-24〜25））

**手順**:

| 順 | 作業 | 場所 | 確認すること |

- 実行の最後に、Supabase の API にテーブルの追加を知らせる（`NOTIFY pgrst, 'reload schema'`）ので、すぐに反映される
