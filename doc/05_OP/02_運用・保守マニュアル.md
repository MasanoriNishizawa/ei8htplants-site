## 1. 日常監視

### ログ確認

本番（Render）では、サーバーに入ってファイルを見る（`tail`・`journalctl` など）ことはできない。ログは Render の画面で見る。

1. https://dashboard.render.com を開いてログインする
2. サイト本体のサービスを選び、左のメニューの **[Logs]** を開く
3. 新しいログが下に流れてくる。上の検索欄に文字を入れると絞り込める

| 見たいもの | 検索欄に入れる例 |
|---|---|
| サーバーのエラー（500 番台） | ` 500 `・`Traceback`・`ERROR` |
| ログインが必要な操作が断られた | ` 401 ` |
| メールの送信の失敗 | `送信に失敗しました`（例「予約の受付メールの送信に失敗しました」「お問い合わせの自動返信の送信に失敗しました」） |
| 予期しない失敗 | `未処理の例外` |
| 公開の書き込みの送りすぎの制限（AI チャット・お問い合わせ・予約・キャンセル・注文） | ` 429 ` |

> Render の Logs に残る期間には限りがある。気になるログは、見つけたときに画面の文字をコピーして残しておく。

**ログに出る内容（2026-10-23 記載）**

- エラーのログには、失敗の種類とコードだけが出る（例 `予約の受付メールの送信に失敗しました: APIError(code=…)`）。お客様が入力した名前・メールアドレスなどは出さない。どの予約・注文かは、管理画面（WS予約の「メール未送信」の印など）で確かめる
- 予期しない失敗（「未処理の例外」と出るもの）だけは、原因を調べるため詳しい内容（`Traceback` から始まる数行）が出る。この中に入力された値が混ざることがあるので、ログの文字をほかの人に渡すときは気をつける
- 秘密の値（`SUPABASE_SERVICE_ROLE_KEY` など）はログに出さない

## 2. バックアップ

### Supabase 自動バックアップ

Supabase Pro プランは毎日自動バックアップ。Free プランは自動バックアップなし（手動が必要）。

**手動バックアップ（Supabase管理画面）:**

```
Supabase管理画面 → Settings → Database → Backups → Capture backup
```

**pg_dump を使った手動バックアップ（接続情報は Supabase → Settings → Database → Connection string）:**

```bash
pg_dump "postgresql://postgres.<project-id>:<password>@aws-0-ap-northeast-1.pooler.supabase.com:5432/postgres" \
  > backup_$(date +%Y%m%d).sql
```

### コードバックアップ

Git リポジトリが最新の状態であること。

```bash
git status   # 未コミットの変更がないことを確認
git log --oneline -5
```

## 3. 障害対応

### 3-1. Admin にログインできない

**症状**: メール・パスワードを入力してもエラーになる、またはログインフォームから進めない。

| 手順 | 操作 |
|---|---|
| 1 | パスワードを確認（Caps Lock・全角入力になっていないか） |
| 2 | `https://status.supabase.com` でSupabase Auth の障害がないか確認 |
| 3 | Supabase管理画面 → Authentication → Users → 対象ユーザーの [...] → [Send password recovery] でパスワードリセットメールを送信 |
| 4 | フロントエンドの VITE_SUPABASE_URL / VITE_SUPABASE_ANON_KEY が正しいか確認 |

---

### 3-2. Admin 操作が 401 Unauthorized になる

**症状**: Admin でログインできているのに、イベント追加・削除などの操作が失敗する。

**原因の特定:**

```bash
# ブラウザのDevTools → Network タブでリクエストを確認
# Authorization ヘッダーが付いているか、値が "Bearer <token>" になっているか確認
```

| 原因 | 対処 |
|---|---|
| セッションが切れている | Admin 画面でログアウト → 再ログイン |
| バックエンドの `auth.py` がSupabaseに接続できない | Render の [Environment] の `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` を確認 |
| Supabase Auth サービス障害 | `https://status.supabase.com` を確認。回復を待つ |

---

### 3-3. ページが表示されない（500エラー）

**症状**: ブラウザに 500 または「Internal Server Error」が表示される。

| 手順 | 操作 |
|---|---|
| 1 | Render → サービス → **[Logs]** で、エラーの時刻の `Traceback`・`ERROR` を探し、エラーの内容を確かめる |
| 2 | Render → サービス → **[Events]** で、直前にデプロイが失敗していないか確かめる（失敗していれば、そのときのログを開いて原因を見る） |
| 3 | Render → サービス → **[Environment]** で、環境変数（`NEXT_PUBLIC_SUPABASE_URL` など。[移行計画書](01_移行計画書.md) の Step 2）が入っているか確かめる（値は画面に出さない・書き写さない） |
| 4 | https://status.supabase.com で Supabase の障害が無いか確かめる |
| 5 | 直らないときは、Render の **[Manual Deploy]** → **[Deploy latest commit]** で入れ直す。最新の変更が原因なら、ひとつ前の正常だった版に戻す（Render の [Events] から前のデプロイを選んで **[Rollback]**、または Git で戻してプッシュ） |

| 原因 | 対処 |
|---|---|
| 環境変数が正しくない・足りない | Render の [Environment] で直して保存する（保存すると自動で再起動する） |
| `frontend/dist/` がコミットされていない | ローカルで `cd frontend && npm run build` → `frontend/dist/` をコミットしてプッシュ |
| Supabase 接続エラー | Supabase ダッシュボードでプロジェクトの状態を確認 |
| Python の依存パッケージの不足 | `backend/requirements.txt` を直してプッシュする（Render がデプロイのときに入れ直す） |

---

### 3-4. お問い合わせ・予約確認メールが届かない

**症状**: フォーム送信は完了（200 OK）するが、メールが届かない。

| 手順 | 確認内容 |
|---|---|
| 1 | Admin → [お問い合わせ] で **DBにデータが保存されているか** 確認（DBに保存されていれば受信はできている） |
| 2 | Resend ダッシュボード → Emails でメール送信ログを確認（Delivered / Failed） |
| 3 | Render の [Environment] で `RESEND_API_KEY` / `CONTACT_TO_EMAIL` / `CONTACT_FROM_EMAIL`（予約のメールは `HABITAT_RESEND_API_KEY` / `HABITAT_FROM_EMAIL` / `HABITAT_ADMIN_EMAIL`）が入っているか確認。Render の [Logs] で `resend`・`email` を検索してエラーを見る |
| 4 | Resend でドメイン認証（`ei8htplants.com`・`habitatoides.com`）が有効か確認。無効なら再認証 |
| 5 | 受信側の迷惑メールフォルダを確認 |

---

### 3-5. サイトが止まった・応答しない

| 手順 | 操作 |
|---|---|
| 1 | Render → サービスの画面の上に出る状態（Live・Failed・Suspended など）を確かめる |
| 2 | 動いているのに応答しないときは、右上の **[Manual Deploy]** の横のメニューから **[Restart service]**（再起動）を選ぶ |
| 3 | デプロイが失敗している（Failed）ときは、[Events] でそのデプロイのログを開いて原因を見る。直してプッシュするか、前の版に **[Rollback]** する |
| 4 | Suspended（停止中）のときは、Render の請求・無料枠（全サービスで月 750 時間）を確かめる。分析ダッシュボードは Streamlit Community Cloud に移したので、Render ではサイト本体だけが動いている |

## 4. セキュリティ対応

### 4-1. キーが漏洩した場合

| 漏洩キー | 即時対処 |
|---|---|
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase → Settings → API → Service Role Key の [Regenerate] でローテーション。Render の [Environment] とローカルの `.env` を新しい値に直す（Render は保存すると自動で再起動する）。分析ダッシュボードの Secrets に入れている場合はそちらも直す |
| `RESEND_API_KEY`・`HABITAT_RESEND_API_KEY` | Resend 管理画面でキーを削除し、新しいキーを発行。Render の [Environment] と `.env` を更新 |
| `SQUARE_ACCESS_TOKEN` | Square の開発者の画面でトークンを作り直す。Render の [Environment] と `.env` を更新 |
| `GEMINI_API_KEY` | Google AI Studio でキーを削除し、新しいキーを発行。Render の [Environment] と `.env` を更新 |
| `VITE_SUPABASE_ANON_KEY` | anon key は公開前提だが、念のため Supabase → Settings → API → [Regenerate] でローテーション可能。フロントエンドを再ビルド（`npm run build`）して `frontend/dist/` をコミット・プッシュ |

### 4-2. 不審なアクセスの調査

Render → サービス → **[Logs]** で、次の文字を検索して増えていないか見る。

| 調べたいこと | 検索する文字 |
|---|---|
| ログインが必要な操作への不正な試し（断られた記録） | ` 401 ` |
| 公開の書き込みの送りすぎ（制限で断った記録。AI チャット・お問い合わせ・予約・キャンセル・注文） | ` 429 ` |
| お問い合わせフォームへの大量の送信 | `POST /api/contact` |

**対処:**
- 本番は Render の上で動いているので、サーバーに入って IP アドレスを止める（nginx・ファイアウォール）ことはできない。特定の相手からの大量のアクセスが続くときは、開発者に連絡して対策（Cloudflare などで止める・アプリの制限を強める）を相談する
- 公開の書き込み（AI チャット・お問い合わせ・WS予約・キャンセル・注文）は、送り元の IP ごとに回数を数えて、多すぎると ` 429 ` で断る。送り元の IP は Cloudflare が付ける印（`CF-Connecting-IP`）などから決めている（2026-10-23 から。それまでは全員が同じ IP として数えられていた）。ただし Render の URL（`〜.onrender.com`）に直接送られると、この印を相手が自由に書けるので、制限をすり抜けられる（課題表 I-19）
- `backend/app/main.py` の CORS（ほかのドメインのページから API を呼ぶ許可）は `localhost:5173`（開発用）だけ。本番は画面と API が同じドメインなので、本番のドメインを足す必要はない

### 4-3. サイトのフォルダの外のファイルを読まれないこと（2026-10-21 追加）

URL の書き方を工夫して（`..%2F` など）、公開用のフォルダ（`frontend/dist`）の外のファイル（`.env` など）を読もうとするアクセスがある。2026-10-21 から、サーバー自身が「実際の場所が `frontend/dist` の中のファイルだけ」を返すようにしている（本番ではその前の段階の Render でも 400 になる）。外を指す URL には、ふつうのページ（`index.html`）が返る。

Render の Logs で `%2F` や `..` を含むリクエストが増えていても、ファイルの中身は返らない。気になるときは、開発者がローカルで `cd backend && python -m pytest tests/test_seo.py` を実行して、外のファイルを返さないテストが通ることを確かめる。

## 5. 保守作業

### 5-1. アプリケーションの更新デプロイ

本番は `main` ブランチにプッシュすると、Render が自動でデプロイする。

1. 画面を変えたときは、ローカルで `cd frontend && npm run build` を実行し、`frontend/dist/` もコミットする
2. `python scripts/run_tests.py --note "何を変えたか"` で全テストが通ることを確かめる
3. `main` にプッシュする
4. Render → サービス → **[Events]** でデプロイが「Deploy live」になるまで待つ（失敗したら [Logs] で原因を見る）
5. 本番のサイトで変更を確かめる

> **2026-10-23 のデプロイの後の注意**: デプロイの前から管理画面を開いたままの端末（パソコン・スマホ）には、古い画面が残っている。その画面で一覧を開くと、一度だけ「〜の読み込みに失敗しました」と出ることがある。そのときはページを再読み込みする（Windows は Ctrl+Shift+R、Mac は Cmd+Shift+R）。新しい画面に入れ替わり、以後は出なくなる。運営メンバーにも伝えておく

> 自動デプロイが動かないとき・同じ版を入れ直したいときは、Render の **[Manual Deploy]** → **[Deploy latest commit]** を押す。

### 5-2. DBマイグレーション（新しいマイグレーションがある場合）

1. `backend/migrations/` の新しいファイルと、ファイルの先頭の説明（実行のタイミング）を読む
2. Supabase 管理画面 → SQL Editor で SQL を貼り付けて実行する
3. 多くの場合はデプロイの前に実行する。デプロイの後に実行するもの（例 `017`）もあるので、[移行計画書](01_移行計画書.md) の 4章・5章に従う
4. 2026-10-23 の `019_security_hardening.sql`（データベースの権限を絞る）は、デプロイの前後どちらで実行してもよい。実行した後に、公開サイトで予約・注文・記事の表示ができることを確かめる（[移行計画書](01_移行計画書.md) の「5-2」）
5. 2026-10-24 の `020_price_calc_entries.sql`（販売価格計算の登録リストのテーブルを作る）も、デプロイの前後どちらで実行してもよい。実行した後に、管理画面の「販売価格計算」で登録リストが読み込めることと、登録・削除ができることを確かめる（[移行計画書](01_移行計画書.md) の「5-3」）

### 5-3. 依存パッケージの更新

ローカルで確かめてからプッシュする（本番の Render はプッシュした `requirements.txt`・`package.json` で入れ直す）。

```bash
# バックエンド（セキュリティアップデート確認）
cd backend
source .venv/bin/activate
pip list --outdated
# 更新例
pip install --upgrade <package>==<new_version>
pip freeze > requirements.txt

# フロントエンド
cd frontend
npm outdated
npm update   # minor/patch のみ自動更新
```

> **注意**: メジャーバージョンアップ（特に supabase-py / @supabase/supabase-js）は API が変わる可能性がある。変更履歴を確認してからローカルでテスト後に反映する。

### 5-5. SNS のプレビューと検索エンジン向けの確認（2026-10-21 追加）

サイトは、ページを返すときにページごとのタイトル・説明・SNS 用の画像（OGP）・検索エンジン向けの情報を入れている（仕組みは [FT-26 検索エンジン・SNS 向けの情報](../01_BD/features/15_検索エンジン・SNS向け情報.md)）。デプロイしたあと、とくにこの仕組みに関わる変更をしたときや、新しいイベントを公開したときに、次の方法で確かめる。

> サーバーはイベント・記事・商品の情報を 60 秒覚えておく。管理画面で直した直後は、1 分ほど待ってから確かめる。

#### (1) サーバーが返す内容を直接見る

```bash
# イベントのページのタイトル・説明・OGP（og:）・X のカード（twitter:）・構造化データ（ld+json）
curl -s https://ei8htplants.com/events/<slug> | grep -E '<title>|og:|twitter:|canonical|robots|ld\+json'

# robots.txt と sitemap.xml
curl -s https://ei8htplants.com/robots.txt
curl -s https://ei8htplants.com/sitemap.xml | head -20

# 管理画面には noindex（検索結果に出さない印）が入っていること
curl -s https://ei8htplants.com/admin | grep 'name="robots"'
```

#### (2) Facebook（シェアデバッガー）

1. https://developers.facebook.com/tools/debug/ を開く（Facebook のアカウントでログインが必要）
2. 確かめたいページの URL（例 `https://ei8htplants.com/events/<slug>`）を入れて **[デバッグ]** を押す
3. 「リンクプレビュー」にタイトル・説明・画像が正しく出ているかを見る
4. 古い内容が出るときは **[もう一度スクレイピング]** を押す（Facebook が覚えている内容を読み直させる）

#### (3) X（旧 Twitter）のカード

X には、カードの見え方を確かめる専用のページが今は無い。X の投稿の作成画面に URL を貼ると、下にカード（画像・タイトル）の見え方が出るので、それで確かめる（**投稿はせず**、確かめたら消す）。

- ページ固有の画像があるページ（イベント・記事・商品など）は大きい画像のカード、無いページはロゴの小さいカードになる
- X は一度読んだ内容をしばらく覚えているので、直した直後は古い内容が出ることがある。時間をおいて確かめる

#### (4) LINE

1. LINE の公式の確認ページ **PagePoker**（https://poker.line.naver.jp/ ）を開く
2. URL を入れ、「Clear Cache」にチェックを入れて **[Poke!]** を押す
3. 表示されたタイトル・説明・画像を確かめる。チェックを入れて実行すると、LINE が覚えている古い内容も読み直される

確かめたあと、自分あてのトーク（Keep メモなど）に URL を送って、実際の見え方も確かめるとよい。

#### (5) Google のリッチリザルトテスト（イベントの構造化データ）

1. https://search.google.com/test/rich-results を開く
2. イベントのページの URL を入れて **[URL をテスト]** を押す
3. 「イベント」が見つかり、エラーが無いことを確かめる
   - 「イベント」が出ないとき: そのイベントに住所が入っていない可能性が高い（住所が無いイベントには、イベントの構造化データを入れない）。管理画面のイベント編集で「住所」を入れるか、イベントページの会場の住所を入れる
   - 日付だけで時刻が無いとき: イベントの「時間」（または日別の時間）に開始と終了の両方の時刻（例「10:00〜17:00」）が入っていない
4. トップページで確かめると「組織（Organization）」が見つかる

細かい内容は https://validator.schema.org/ に URL を入れても確かめられる。

#### (6) Google Search Console に sitemap を登録する（最初に1回）

Search Console は、Google 検索でのサイトの状態（どのページが載っているか・エラー）を見られる Google の無料のサービス。

1. https://search.google.com/search-console を開き、サイトを管理する Google アカウントでログインする
2. `ei8htplants.com` のプロパティがまだ無ければ、**[プロパティを追加]** で追加し、画面の案内に従って所有者であることを確かめる（ドメインの設定に Google から指定された文字列を追加する、など）
3. 左のメニューの **[サイトマップ]** を開く
4. 「新しいサイトマップの追加」に `sitemap.xml` と入れて **[送信]** を押す
5. 「送信されたサイトマップ」の一覧で、ステータスが「成功しました」になり、「検出されたページ数」が出ることを確かめる（反映まで数日かかることがある）

登録は1回でよい。そのあとイベント・記事・商品を追加すると、`sitemap.xml` には自動で載る（Google が定期的に読みに来る）。

- 特定のページが検索に載っているかは、上の検索欄（**URL 検査**）に URL を入れて確かめる。載っていなければ **[インデックス登録をリクエスト]** を押す
- 管理画面・予約キャンセル・購入手続き・注文完了のページは、わざと検索結果に出さない（noindex）。「noindex タグによって除外されました」と出ても問題ない。存在しないイベントなどの URL も同じ扱い

## 6. 連絡体制

| 状況 | 連絡先 | 目安対応時間 |
|---|---|---|
| サイト停止・致命的障害 | 開発者に直接連絡（緊急） | 即時対応 |
| 機能不具合・表示崩れ | 開発者にメール or 口頭 | 1〜3営業日 |
| コンテンツ更新（イベント等） | 管理者が Admin 画面から自己対応 | 即時 |
| 機能追加依頼 | 開発者に相談 | 要見積もり |
