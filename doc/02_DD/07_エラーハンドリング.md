# DD-07 — エラーハンドリング

## 1. フロントエンド — APIクライアント (`lib/api.ts`)

### エラー生成ルール（2026-10-22 に今のコードに合わせた）

```typescript
async function fetchOk(path: string, options?: RequestInit): Promise<Response> {
  const res = await fetch(`${BASE}${path}`, { ... })
  if (!res.ok) {
    // 本文が JSON で detail があれば「404 見つかりません」、無ければ「404 Not Found」
    throw new ApiError(res.status, msg, detail)
  }
  return res
}
```

- HTTPステータスが 2xx 以外のとき `ApiError` を投げる。`status`（状態コード）と `detail`（サーバーの説明。文字か、422 では項目ごとの配列）を持つ
- `message` は「状態コード 説明」の形（例 `"404 イベントが見つかりません"`）。状態コードだけ欲しいときは `lib/httpError.ts` の `httpStatusOf(err)` で読む
- ネットワーク断（fetch自体の失敗）は `TypeError: Failed to fetch` がスローされる
- 公開の AI チャット（`api.chat.send`）とキャンセル（`api.reserve.cancel`）は、状態コードで案内を分けるため、失敗でも投げずに応答（Response）をそのまま返す

### 画面に出す文言

- `message` は開発者向けの形（422 では英語の配列が入る）なので、画面にそのまま出さない
- 公開ページ: 送信の失敗は画面ごとに状態コードで文言を決める（予約 [FT-06](../01_BD/features/06_予約フォーム.md)・購入 [PG-16](../01_BD/pages/public/16_Checkout.md)）。読み込みの失敗は共通の `components/LoadError.tsx`
- 管理画面: 3章の「管理画面の失敗の文言」

### サーバーの文言に合わせて出し分けている箇所（2026-10-23 追加）

次の画面は、サーバーの説明（`detail`）の文字を見て文言を出し分けている。**サーバーの文言を変えるときは画面も合わせて直す**（合わないと共通の文言になり、利用者に正しい案内が出ない）。

| 画面 | 見ている文字 | サーバーの場所 |
|---|---|---|
| 予約（`pages/Reserve.tsx`） | 400 の「このイベントの予約受付は終了しています」「この日の予約受付は終了しています」「予約日がイベントの開催期間外です」「ワークショップの時間枠が正しくありません」（完全一致） | `backend/app/routes/reserve.py` |
| 購入（`pages/Checkout.tsx`・`lib/checkout/orderErrorMessage.ts`） | 500 の説明に「お支払いは完了」、502 の説明に「確認できませんでした」が入っているか | `backend/app/routes/orders.py` |
| 管理画面（`pages/admin/errorMessage.ts`） | 422 の配列の項目名（`name`・`price` など）を日本語の名前にする | 各 `routes/*.py` の入力の型 |

## 2. フロントエンド — フォームページの statusマシン

### 対象ページ
- `pages/Contact.tsx`
- `pages/Reserve.tsx`

### 状態定義

```
idle ──[送信]──► loading ──[成功]──► done
                         └──[失敗]──► error
```

| status | 意味 | UI表示 |
|---|---|---|
| `idle` | 初期状態・入力受付中 | フォーム表示、ボタン有効 |
| `loading` | API呼び出し中 | フォーム表示、ボタン disabled |
| `done` | 送信成功 | 完了メッセージ表示 |
| `error` | 送信失敗 | フォーム表示、エラーメッセージ表示 |

### 実装パターン

```typescript
const [status, setStatus] = useState<'idle' | 'loading' | 'done' | 'error'>('idle')

const handleSubmit = async (e: React.FormEvent) => {
    e.preventDefault()
    setStatus('loading')
    try {
        await api.contact.send(form)
        setStatus('done')
        setForm({ name: '', email: '', message: '' })  // フォームリセット
    } catch {
        setStatus('error')
    }
}
```

## 3. フロントエンド — 管理画面のエラーハンドリング

### 管理画面の失敗の文言（`pages/admin/errorMessage.ts`、2026-10-22 追加）

```typescript
failMessage('保存に失敗しました', e)
// → 「保存に失敗しました（見つかりませんでした（削除された可能性があります））」
```

`failMessage(何に失敗したか, 失敗)` は「何に失敗したか（理由）」の形の文言を作る。理由（`reasonOf`）は次のとおり。

| 失敗 | 理由の文言 |
|---|---|
| 401（ApiError）、またはログインのトークンが無い（`401 Unauthorized`） | ログインの期限が切れました。ログインし直してください |
| 404 | 見つかりませんでした（削除された可能性があります） |
| 422（入力チェック） | 入力内容を確認してください: 価格: 0 以上にしてください、… （項目名は `FIELD_LABELS` で日本語にする。種類ごとに「入力してください」「〜以上にしてください」「整数を入れてください」「長すぎます」「選べる値ではありません」など） |
| 400・409 などで説明が文字 | サーバーの説明（日本語）をそのまま |
| それ以外 | 失敗の message（通信の失敗など） |

- 状態コードだけで分けたいときは `statusOf(e)`（例: 予約の状態の変更で 409 のときは「満席のため受付済に戻せません」）

### データ取得失敗（2026-10-22 変更）

一覧を読み込めなかったときは、赤い枠（`role="alert"`）で「〜の読み込みに失敗しました（理由）」を出し、「データがありません」「まだ登録されていません」は出さない（失敗を0件と見せない）。2026-10-22 までは多くの画面で何も出さず、空の一覧に見えていた。

| 画面 | 読み込みに失敗したとき |
|---|---|
| イベント一覧・取扱店・コラボ・価格計算・収支・WS集計 | 上に赤い枠の文言（一覧の部分は空） |
| 支払い集計 | 表の代わりに赤い枠の文言だけ |
| 鉢作家・メディア | 一覧の代わりに赤い枠の文言と「再読み込み」ボタン |
| イベントサイト編集 | フォームを出さずに赤い枠の文言と「再読み込み」ボタン（空のフォームで上書き保存するのを防ぐ） |
| 管理情報の編集・収支の入力 | 赤い文言を出し、「保存する」を押せなくする（2026-10-16 から） |
| イベント別予約 | 予約一覧が読めなければ赤い枠。時間枠だけ読めなければ注意文を出して一覧は出す |
| 設計書 | 本文の欄に赤字（「設計書ツリーの取得に失敗しました」「ファイルの取得に失敗しました」） |

ダッシュボードの「出店料の支払い」「今後の搬入予定」（2026-10-21 追加）は、読み込みに失敗すると「読み込みに失敗しました。時間をおいて再度お試しください。」を赤字で出す。件数のカードとは別に読み込むので、片方が失敗してももう片方は表示される。

### ページのファイルの読み込み失敗（2026-10-21 追加）

画面ごとに分けたファイルの読み込みに失敗したとき（新しい版の公開で古いファイルが消えた・通信が切れたなど）は、`main.tsx` が1回だけ再読み込みし（10秒以内の2回目はしない）、それでも失敗したら `LoadErrorBoundary` が「ページを読み込めませんでした。再読み込みしてください。」と「再読み込み」ボタンを出す。エラーは `console.error('画面の読み込みに失敗しました', ...)` でコンソールに出す。詳しくは [DD-03](03_フロントエンドロジック.md) 21節。

### CRUD操作失敗（2026-10-22 変更）

追加・保存・削除・アップロードは `try/catch` で囲み、失敗したら `failMessage` の文言を赤い枠で出す。入力は残すので、直してもう一度押せる。削除に失敗したときは一覧から外さない。イベント一覧の複製・削除は、処理中は全部の行のボタンを押せなくする（二重に作らないため）。

### 予約ステータス更新（2026-10-22 変更）

```typescript
const updateStatus = async (id: string, status: string) => {
    setUpdating(id)          // 更新中の行のプルダウンを押せなくする
    setPageError('')
    try {
        const updated = await api.reserve.updateStatus(id, status)
        setRows(prev => prev.map(r => r.id === id ? { ...r, ...updated } : r))
    } catch (e) {
        // 画面の状態は変えない（2026-10-22 まではここで画面だけ変えていた）
        setPageError(statusOf(e) === 409
            ? failMessage('満席のため受付済に戻せません。元の状態のままです', e)
            : failMessage('ステータスの変更に失敗しました。元の状態のままです', e))
    } finally {
        setUpdating(null)
    }
}
```

## 4. バックエンド — HTTPException

### 使用ルール

```python
from fastapi import HTTPException

# 404 Not Found（リソース未存在）
if not data:
    raise HTTPException(404)

# 500 Internal Server Error（設定エラー）
if not RESEND_API_KEY or not CONTACT_TO_EMAIL:
    raise HTTPException(500, 'Mail not configured')
```

### レスポンス形式

FastAPI のデフォルト形式:

```json
{ "detail": "Not Found" }
{ "detail": "Mail not configured" }
```

## 5. バックエンド — Pydantic バリデーションエラー

Pydantic モデルの型検証に失敗した場合、FastAPI が自動で `422 Unprocessable Entity` を返す。

```json
{
  "detail": [
    {
      "type": "missing",
      "loc": ["body", "name"],
      "msg": "Field required",
      "input": {}
    }
  ]
}
```

対象フィールド例:
- `name: str` (required) → 未指定時に422
- `email: EmailStr` → メール形式違反時に422
- `participants: int` → 数値以外で422

## 6. バックエンド — Supabase クライアントエラー

Supabase Python SDK のエラーは例外としてスローされ、FastAPI がキャッチして `500` を返す。

| エラー原因 | 発生条件 |
|---|---|
| 接続エラー | SUPABASE_URL が不正または到達不可 |
| 認証エラー | SUPABASE_ANON_KEY / SERVICE_ROLE_KEY が不正 |
| RLS違反 | anon クライアントで書き込みを試みた場合 |
| `.data[0]` IndexError | UPDATEが0件だった場合（IDが存在しない） |

## 8. ログ出力ルール

現在のログ実装（2026-10-23 に今のコードに合わせた）:
- FastAPI デフォルトの uvicorn アクセスログ（リクエストメソッド・パス・ステータスコード）
- フロントエンドは `console.error` のみ（ブラウザ開発者ツールに出力）
- バックエンドは Python の `logging` でログを出す（Render のログの画面で見られる）
  - **エラーのログには、例外の種類とコードだけを出す**（`backend/app/utils/errors.py` の `error_summary(e)` → 例 `APIError(code=23505)`・`ConnectionError`）。メール送信や DB の例外の文字には、利用者が入力したメールアドレス・名前などが入ることがあるため、例外の文字そのものは出さない
  - 秘密の値（`SUPABASE_SERVICE_ROLE_KEY` など）はログに出さない
  - ルートで捕まえていない例外（予期しない失敗）は `main.py` の `catch_unhandled_errors` が受け、原因を調べるため `logger.exception('未処理の例外（メソッド パス）')` で詳細（traceback）をログに残す。利用者には「サーバーでエラーが発生しました。時間をおいて再度お試しください。」の 500 だけを返す（内部の情報は返さない）。traceback に入力の値が出る可能性は残る（[PM-04](../03_PM/04_課題・リスク管理表.md) の課題）

## 9. リトライ制御

| 層 | リトライ |
|---|---|
| フロントエンド (`lib/api.ts`) | リトライなし。失敗時に即座にエラーをスロー |
| バックエンド → Supabase | リトライなし。`supabase-py` のデフォルト動作に従う |
| バックエンド → Resend | リトライなし。`resend.Emails.send()` の1回呼び出しのみ |

## 10. フロントエンド認証エラー（AdminLayout）

```typescript
// Supabase が未設定（環境変数なし）
if (!supabase) {
    setError('Supabase not configured')
    return
}

// ログイン失敗（パスワード誤り等）
const { error } = await supabase.auth.signInWithPassword({ email, password })
if (error) {
    setError(error.message)    // Supabaseのエラーメッセージをそのまま表示
    return
}
```

エラーメッセージ例（Supabase Auth が返す）:
- `"Invalid login credentials"` — メール・パスワード不一致
- `"Email not confirmed"` — メール未確認（通常は起こらない）
