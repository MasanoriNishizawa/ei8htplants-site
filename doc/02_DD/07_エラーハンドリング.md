# DD-07 — エラーハンドリング

## 1. フロントエンド — APIクライアント (`lib/api.ts`)

### エラー生成ルール

```typescript
async function request<T>(path: string, options?: RequestInit): Promise<T> {
  const res = await fetch(`${BASE}${path}`, { ... })
  if (!res.ok) throw new Error(`${res.status} ${res.statusText}`)
  return res.json()
}
```

- HTTPステータスが 2xx 以外のとき `Error` をスローする。
- エラーメッセージは `"404 Not Found"` のように `status statusText` 形式。
- ネットワーク断（fetch自体の失敗）は `TypeError: Failed to fetch` がスローされる。

## 2. フロントエンド — フォームページの statusマシン

### 対象ページ
- `pages/Contact.tsx`
- `pages/Reserve.tsx`

### 状態定義

```
idle ──[送信]──► loading ──[成功]──► done
                         └──[失敗]──► error
```

| status | 意味 | UI表示 |
|---|---|---|
| `idle` | 初期状態・入力受付中 | フォーム表示、ボタン有効 |
| `loading` | API呼び出し中 | フォーム表示、ボタン disabled |
| `done` | 送信成功 | 完了メッセージ表示 |
| `error` | 送信失敗 | フォーム表示、エラーメッセージ表示 |

### 実装パターン

```typescript
const [status, setStatus] = useState<'idle' | 'loading' | 'done' | 'error'>('idle')

const handleSubmit = async (e: React.FormEvent) => {
    e.preventDefault()
    setStatus('loading')
    try {
        await api.contact.send(form)
        setStatus('done')
        setForm({ name: '', email: '', message: '' })  // フォームリセット
    } catch {
        setStatus('error')
    }
}
```

## 3. フロントエンド — 管理画面のエラーハンドリング

### データ取得失敗

管理画面の一覧取得（`useEffect`内）では、エラー時に `console.error` を出力するが、ユーザーへの明示的なエラー表示は実装していない（データなし＝空リスト表示）。

```typescript
useEffect(() => {
    api.xxx.list().then(setItems).catch(console.error)
}, [])
```

ダッシュボードの「出店料の支払い」「今後の搬入予定」（2026-10-21 追加）は例外で、読み込みに失敗すると `infoError` を true にし、「読み込みに失敗しました。時間をおいて再度お試しください。」を赤字で出す。件数のカードとは別に読み込むので、片方が失敗してももう片方は表示される。

### ページのファイルの読み込み失敗（2026-10-21 追加）

画面ごとに分けたファイルの読み込みに失敗したとき（新しい版の公開で古いファイルが消えた・通信が切れたなど）は、`main.tsx` が1回だけ再読み込みし（10秒以内の2回目はしない）、それでも失敗したら `LoadErrorBoundary` が「ページを読み込めませんでした。再読み込みしてください。」と「再読み込み」ボタンを出す。エラーは `console.error('画面の読み込みに失敗しました', ...)` でコンソールに出す。詳しくは [DD-03](03_フロントエンドロジック.md) 21節。

### CRUD操作失敗

削除・追加等の操作では `try/catch` なしで `await` している場合がある。APIエラー時は未処理の Promiserejection となる（ブラウザコンソールに出力）。

### 予約ステータス更新の `updating` ガード

```typescript
const [updating, setUpdating] = useState<string | null>(null)

const handleStatusChange = async (id: string, value: string) => {
    if (updating !== null) return   // 更新中は二重送信防止
    setUpdating(id)
    try {
        await api.reserve.updateStatus(id, value)
        setReservations(prev => prev.map(r => r.id === id ? {...r, status: value} : r))
    } finally {
        setUpdating(null)
    }
}
```

### お問い合わせ楽観的更新のエラー

```typescript
// 即時ローカル更新
setContacts(prev => prev.map(x => x.id === id ? {...x, is_read: !c.is_read} : x))
// バックグラウンドAPI呼び出し
api.contact.markRead(id, !c.is_read).catch(console.error)
// エラー時のロールバックは未実装
```

## 4. バックエンド — HTTPException

### 使用ルール

```python
from fastapi import HTTPException

# 404 Not Found（リソース未存在）
if not data:
    raise HTTPException(404)

# 500 Internal Server Error（設定エラー）
if not RESEND_API_KEY or not CONTACT_TO_EMAIL:
    raise HTTPException(500, 'Mail not configured')
```

### レスポンス形式

FastAPI のデフォルト形式:

```json
{ "detail": "Not Found" }
{ "detail": "Mail not configured" }
```

## 5. バックエンド — Pydantic バリデーションエラー

Pydantic モデルの型検証に失敗した場合、FastAPI が自動で `422 Unprocessable Entity` を返す。

```json
{
  "detail": [
    {
      "type": "missing",
      "loc": ["body", "name"],
      "msg": "Field required",
      "input": {}
    }
  ]
}
```

対象フィールド例:
- `name: str` (required) → 未指定時に422
- `email: EmailStr` → メール形式違反時に422
- `participants: int` → 数値以外で422

## 6. バックエンド — Supabase クライアントエラー

Supabase Python SDK のエラーは例外としてスローされ、FastAPI がキャッチして `500` を返す。

| エラー原因 | 発生条件 |
|---|---|
| 接続エラー | SUPABASE_URL が不正または到達不可 |
| 認証エラー | SUPABASE_ANON_KEY / SERVICE_ROLE_KEY が不正 |
| RLS違反 | anon クライアントで書き込みを試みた場合 |
| `.data[0]` IndexError | UPDATEが0件だった場合（IDが存在しない） |

## 7. バックエンド — 環境変数未設定時の挙動

| 変数 | 未設定時の挙動 |
|---|---|
| `SUPABASE_URL` / `SUPABASE_ANON_KEY` | `create_client('')` → 接続失敗、全APIが500 |
| `SUPABASE_SERVICE_ROLE_KEY` | `admin_supabase` の書き込み操作が失敗 |
| `RESEND_API_KEY` | `POST /api/contact` が即座に `500 Mail not configured` |
| `CONTACT_TO_EMAIL` | 同上 |

## 8. ログ出力ルール

現在のログ実装:
- FastAPI デフォルトの uvicorn アクセスログ（リクエストメソッド・パス・ステータスコード）
- フロントエンドは `console.error` のみ（ブラウザ開発者ツールに出力）
- バックエンドのアプリケーションログは未実装（例外はuvicornのスタックトレースとして出力）

## 9. リトライ制御

| 層 | リトライ |
|---|---|
| フロントエンド (`lib/api.ts`) | リトライなし。失敗時に即座にエラーをスロー |
| バックエンド → Supabase | リトライなし。`supabase-py` のデフォルト動作に従う |
| バックエンド → Resend | リトライなし。`resend.Emails.send()` の1回呼び出しのみ |

## 10. フロントエンド認証エラー（AdminLayout）

```typescript
// Supabase が未設定（環境変数なし）
if (!supabase) {
    setError('Supabase not configured')
    return
}

// ログイン失敗（パスワード誤り等）
const { error } = await supabase.auth.signInWithPassword({ email, password })
if (error) {
    setError(error.message)    // Supabaseのエラーメッセージをそのまま表示
    return
}
```

エラーメッセージ例（Supabase Auth が返す）:
- `"Invalid login credentials"` — メール・パスワード不一致
- `"Email not confirmed"` — メール未確認（通常は起こらない）
