## 1. イベント作成 — 画像カスケード処理

### 処理フロー (`routes/events.py`)

```
POST /api/events  body: EventBody

create_event(body):
    1. body.model_dump(exclude={'image_urls'}) でimage_urlsを除いたdictを生成
    2. admin_supabase.table('events').insert(row) → result (UUIDが返る)
    3. _save_images(result['id'], body.image_urls) 呼び出し
    4. get_event(result['id']) を返す（imageを含む完全データ）

_save_images(event_id, urls):
    if not urls: return  # 画像なしは即リターン
    rows = [
        {'event_id': event_id, 'url': url, 'display_order': i}
        for i, url in enumerate(urls)
    ]
    admin_supabase.table('event_images').insert(rows).execute()
    // enumerate → display_order は 0-indexed
```

### イベント更新 — 画像全置換

```
PUT /api/events/{event_id}  body: EventBody

update_event(event_id, body):
    1. eventsテーブルを update
    2. event_images を DELETE WHERE event_id = event_id  (全削除)
    3. _save_images(event_id, body.image_urls)  (再挿入)
    4. get_event(event_id) を返す

// 差分更新ではなく全置換。画像の順序変更もこのフローで対応。
```

### イベント取得 — _attach_images

```
_attach_images(events: list[dict]) → list[dict]:
    if not events: return events

    ids = [e['id'] for e in events]

    // N+1を避けるため IN句で一括取得
    imgs = supabase.table('event_images')
                   .select('*')
                   .in_('event_id', ids)
                   .order('display_order')
                   .execute().data

    // event_idをキーにグルーピング
    img_map: dict[str, list] = {}
    for img in imgs:
        img_map.setdefault(img['event_id'], []).append(img)

    // 各イベントに images プロパティを付与
    for e in events:
        e['images'] = img_map.get(e['id'], [])

    return events
```

## 2. お問い合わせ — 二重書き込みフロー

### 処理フロー (`routes/contact.py`)

```
POST /api/contact  body: ContactBody

send_contact(body):
    1. 設定チェック
       if not RESEND_API_KEY or not CONTACT_TO_EMAIL:
           raise HTTPException(500, 'Mail not configured')

    2. DB保存 (admin_supabase 使用)
       admin_supabase.table('contacts').insert(body.model_dump()).execute()
       // body.model_dump() = {name, email, message}
       // is_read は DEFAULT false, created_at は DEFAULT now()

    3. メール送信 (Resend SDK)
       resend.api_key = RESEND_API_KEY
       resend.Emails.send({
           'from': CONTACT_FROM_EMAIL,
           'to': [CONTACT_TO_EMAIL],
           'reply_to': body.email,    // 返信先を問い合わせ者のメールに設定
           'subject': f'[ei8ht plants] お問い合わせ: {body.name}',
           'text': f'お名前: {body.name}\nメール: {body.email}\n\n{body.message}',
       })

    4. return {'ok': True}
```

### 注意点

- DB保存とメール送信はトランザクションで保護されていない。
- DB保存成功・メール失敗の場合: HTTP 500 が返るが DBにはレコードが残る。
  → 管理画面 `/admin/contacts` でレコードは確認できる。
- DB保存失敗の場合: Supabase例外がそのまま HTTP 500 となる。

## 5. 予約ステータス更新とキャンセルリンク送信

### 処理フロー (`routes/reserve.py`。2026-10-23 に今のコードに合わせた)

```
PATCH /api/reserves/{reservation_id}  body: ReserveStatusPatch（status は 'pending' | 'confirmed' | 'cancelled' だけ受け付ける）

update_reservation_status(reservation_id, body):
    1. 現在の行を取得（無い・ID の形が違う → 404）
    2. status が今と同じ → 何もせず今の行を返す（メールも送らない）
    3. キャンセルから戻す（今が 'cancelled'）かつ時間枠あり
         → _session_lock(session_id) の中で満席を確かめる
            満席 → 409「この時間枠は満席のため、キャンセルを取り消せません」
            空きあり → status を更新
       それ以外 → status を更新
    4. _sync_reserved_count_safely(session_id)（時間枠の人数を数え直す）
    5. 'cancelled' に変えたときだけ _send_cancel_confirmation(row)（失敗してもログだけ）
    6. 更新後の行を返す
```

- キャンセルトークンは、予約を受け付けたとき（`POST /api/reserve`）と当日参加の登録のときに `_generate_cancel_token()` で作る。状態を変えても作り直さない
- `_generate_cancel_token()` は `secrets.token_urlsafe(16)`（英数字と `-` `_` の約22文字。推測されにくい）。2026-10-22 までは8桁の数字で、その古いトークンもキャンセルにそのまま使える
- `confirmed` は当日参加（`add_walkin`）の予約で使う。画面では `pending` と同じ「受付済」

### キャンセルフロー

```
POST /api/reserve/cancel  body: CancelBody { token: 1〜64 文字 }

cancel_by_token(body, request):
    1. cancel_limiter.check(client_ip(request))（1 分間に 5 回まで。超えたら 429。総当たり対策）
    2. cancel_token で全行を取得（created_at 降順）
    3. 行なし → 404「キャンセルIDが見つかりません」
    4. 最新の非キャンセル行を選択
       なし → 400「この予約はすでにキャンセル済みです」
    5. status = 'cancelled' に更新し、_sync_reserved_count_safely(session_id)
    6. キャンセルのメールを送る（失敗してもログだけ）
    7. {"ok": true} を返す（予約者の情報は返さない）
```

- 同じトークンが複数の行にあるのは、古い8桁の数字のトークンが重なったときだけ。そのときは最新の未キャンセルの行を対象にする

## 7. JST タイムゾーン処理（`routes/events.py`）

サーバーは UTC で動作するため、日本時間の日付判定には共通の関数 `today_jst()`（`backend/app/utils/dates.py`）を使用する。

```python
from datetime import datetime, timezone, timedelta

JST = timezone(timedelta(hours=9))

def today_jst() -> str:
    return datetime.now(_JST).date().isoformat()
```

- `date.today()` は UTC 基準のため JST 深夜 0〜9 時の間に誤判定が発生する。
- `today_jst()` を全ての日付比較（`is_past` 計算、`list_events` フィルタ、`get_event`）で使用する。

## 10. 予約定員チェック — スレッドロックによる原子化（`routes/reserve.py`）

同一セッションへの同時送信でオーバーブッキングが起きないよう、
セッション単位の `threading.Lock` でチェック→INSERTを直列化する。

```python
# 時間枠 ID → ロックと「今使っている処理の数」（2026-10-23 変更）
_session_locks: dict[str, _LockEntry] = {}
_session_locks_mu = threading.Lock()

@contextmanager
def _session_lock(session_id):
    1. _session_locks_mu の中で、ロックを取り出し（無ければ作り）、使う数を 1 増やす
    2. そのロックを取って with の中（満席の確認と保存）を実行する
    3. 終わったら（失敗しても）使う数を 1 減らし、0 になったら辞書から消す
       （使用中のロックは消さないので、同じ時間枠の処理が別々のロックを取ることはない）

def create_reservation(body):
    if body.session_id:
        # 先に時間枠がこのイベントのものかを確かめる（無い・別のイベントなら 400。ロックは取らない）
        session = _load_session_for_event(body.session_id, body.event_id)
        with _session_lock(body.session_id):
            used = _session_used_count(...)   # session_id + preferred_time フォールバック
            if used + body.participants > session['max_participants']:
                raise HTTPException(409, 'このセッションは満席です')
            row = admin_supabase.table('workshop_reservations').insert(...).execute().data[0]
    else:
        row = admin_supabase.table('workshop_reservations').insert(...).execute().data[0]
```

- それまでは、存在するか確かめる前の時間枠 ID でもロックを作り、使い終わっても辞書に残していた。でたらめな ID を送られるとロックが増え続けるため、確かめてから取り、使い終わったら消すようにした（2026-10-23）
- 管理画面で予約をキャンセルから受付済に戻すとき（`update_reservation_status`）も、同じロックの中で満席を確かめる（満席なら 409）

**制約**: 単一プロセス内でのみ有効（Render 単一インスタンス構成を前提）。
マルチプロセス構成になった場合は DB レベルのロック（PostgreSQL Advisory Lock 等）が必要。

定員チェックは `participants` カラムの合計値（行数ではなく人数）で判定し、
`session_id` が無い古い予約は `preferred_time` フォールバックで加算する。

## 12. SPA フォールバック（本番）

### `backend/app/main.py`

```python
DIST = os.path.join(os.path.dirname(__file__), '../../frontend/dist')

if os.path.isdir(DIST):
    # 静的ディレクトリを個別マウント
    for _subdir in ['assets', 'img', 'favicon']:
        _path = os.path.join(DIST, _subdir)
        if os.path.isdir(_path):
            app.mount(f'/{_subdir}', StaticFiles(directory=_path), name=_subdir)

    # SPA の index.html（全ページ共通の入口）
    INDEX_HTML = os.path.join(DIST, 'index.html')

    # SPAフォールバック: dist の中にあるファイルはそのまま返し、それ以外はメタ情報入りの index.html
    @app.get('/{full_path:path}')
    def serve_spa(full_path: str, request: Request):
        # 1. 実際の場所に直してから、dist の中にあるときだけファイルを返す（2026-10-21 修正）
        dist_real = os.path.realpath(DIST)
        file_path = os.path.realpath(os.path.join(dist_real, full_path))
        if file_path.startswith(dist_real + os.sep) and os.path.isfile(file_path):
            return FileResponse(file_path)
        # 2. パスに応じたメタ情報を index.html に入れて返す（2026-10-21 追加。14節）
        try:
            return HTMLResponse(seo.render_spa_index(INDEX_HTML, full_path, dict(request.query_params)))
        except Exception as e:
            # 3. 失敗しても SPA は表示できるよう、元の index.html を返す
            logger.error('serve_spa メタ情報の埋め込みエラー（%s）: %s', full_path, e)
            return FileResponse(INDEX_HTML)
```

- Vite ビルド済みSPAを FastAPI 単体で配信するための設定。
- `/{full_path:path}` はAPI routerより後に登録されているため、`/api/*` はAPIが処理する。`seo.router`（`/robots.txt`・`/sitemap.xml`）も `serve_spa` より前に登録している。
- `frontend/dist` が存在しない開発時はこのブロックは実行されない。

### dist の外のファイルを返さない（2026-10-21 修正）

以前は `os.path.join(DIST, full_path)` をそのまま使っていたため、`..%2F`（`../` を URL の書き方で表したもの）や `%2Fetc%2F…`（`/` 始まりのパス）のような URL で、dist の外のファイル（`.env`・ソースなど）を返せてしまうおそれがあった。本番では前段（Render）で 400 になっていたが、サーバー自身でも防ぐ。

1. `os.path.realpath` で `..` やリンクをたどった実際の場所に直す
2. 実際の場所が `dist の実際の場所 + 区切り文字` で始まり、ファイルとして存在するときだけ `FileResponse` で返す
3. 外を指していたら、ファイルは返さず SPA の `index.html`（メタ情報入り）を返す

## 13. 公開 AI チャットの入力チェック（`routes/chat.py`、2026-10-20 追加）

公開チャット（`POST /api/chat`）は誰でも送れるため、長い文や長い会話を送られると AI（Gemini）の利用料が増える。そこで、受け取った内容をリクエストの型（Pydantic）で確かめ、条件に合わなければ処理に入る前に `422` を返す。

### 定数

| 定数 | 値 | 意味 |
|---|---|---|
| `MAX_MESSAGE_CHARS` | 2000 | 1件の本文の最大文字数。植物の相談や予約の質問なら足りる長さ |
| `MAX_MESSAGES` | 40 | 1回で送れる会話の最大件数（約 20 往復。ウェルカムメッセージと AI の返事も数える） |

### 型と条件

```python
class Message(BaseModel):
    role: Literal['user', 'model']                                   # 'user' と 'model' 以外は 422
    content: str = Field(min_length=1, max_length=MAX_MESSAGE_CHARS)  # 1〜2,000 文字
    # _content_not_blank: 空白・改行だけなら 422（値そのものは削らずに返す）

class ChatRequest(BaseModel):
    messages: list[Message] = Field(min_length=1, max_length=MAX_MESSAGES)  # 1〜40 件
    # _last_message_is_user: 最後のメッセージが 'user' でなければ 422
```

- 文字数は Python の文字数（絵文字も 1 文字）で数える。画面側の `clampContent` も同じ数え方で切る
- 前後の空白・改行は削らず、そのまま Gemini に渡す
- 最後が AI の発言だと「今回の質問」が無いまま料金だけかかるため、最後は利用者の発言に限る

### 処理の順番

```
リクエスト受信
    │
    ├─ 入力チェック（上の条件）に合わない → 422（chat() 関数に入らない）
    │     → Gemini を呼ばない・送信回数（_request_log）にも数えない
    │
    ├─ GEMINI_API_KEY が無い → 503
    ├─ IP ごとの回数制限（1 分間に 10 回）を超えた → 429
    └─ Gemini に送信 → { reply } を返す（失敗は 500）
```

以前は `messages` が空でも型の確認を通り、`body.messages[-1]` で失敗して `500` になっていた。今は入力チェックで `422` になる。

## 14. 検索エンジン・SNS 向けの情報（`routes/seo.py`、2026-10-21 追加）

画面の見え方・値の一覧は [FT-26 検索エンジン・SNS 向けの情報](../01_BD/features/15_検索エンジン・SNS向け情報.md) を参照。ここでは処理の流れを書く。

### 定数

| 名前 | 値 | 用途 |
|---|---|---|
| `SITE_ORIGIN` | `https://ei8htplants.com` | canonical・`og:url`・画像の絶対 URL の土台 |
| `SITE_NAME` | `ei8ht plants` | タイトルの末尾・`og:site_name` |
| `DEFAULT_DESCRIPTION` / `DEFAULT_OG_IMAGE` | `PageMeta.tsx` と同じ | ページ固有の値が無いとき |
| `CACHE_TTL_SECONDS` | 60 | DB の読み取り結果・sitemap を覚えておく秒数 |
| `CACHE_MAX_ENTRIES` | 500 | 覚えておく件数の上限（存在しない ID を大量に送られてもメモリが増え続けない） |
| `DESCRIPTION_MAX_LEN` | 120 | 説明文の最大文字数 |
| `EVENT_JSONLD_MAX_IMAGES` | 5 | イベントの構造化データに入れる画像の最大枚数 |
| `NOINDEX_PREFIXES` / `ROBOTS_DISALLOW` | `/admin`・`/cancel`・`/checkout`・`/order` | noindex を入れる・robots.txt で Disallow にするパス |
| `STATIC_PAGES` | パス → `StaticPage(title, description, image)` | 固定ページの値（各ページの `<PageMeta>` を写したもの） |
| `SITEMAP_STATIC_PATHS` | 固定ページ 17 件 | sitemap.xml に載せる固定ページ |

### 処理の流れ（render_spa_index）

```
serve_spa(full_path, request)
    └─ seo.render_spa_index(INDEX_HTML, full_path, query)
          1. _read_index(): index.html を読む（更新時刻が同じなら前回の中身を使う）
          2. build_page_meta(path, query): パスに応じた PageMeta を決める
          3. inject_head(): index.html の <title>…</title> を render_head_tags() の結果に置き換える
                            （<title> が無ければ </head> の前に入れる）

build_page_meta(path, query)
    パスを "/a/b" の形にそろえる（末尾のスラッシュは外す）
    try:
      1. /events/{key}  → _fetch_event(key)
           見つかり、名前がある → タイトル=イベント名、説明=_event_description、画像=1枚目
                                   slug があれば canonical は /events/{slug}
                                   _event_json_ld() が作れたら json_ld に追加
           無い → _not_found_meta()
      2. /journal/{id}  → _fetch_article(id)（公開中だけ）
           ある → タイトル「記事名 | Journal」、説明=本文の先頭、画像=本文の最初の画像か image_urls[0]
           無い → _not_found_meta()
      3. /shop/{id}     → _fetch_product(id)（公開中だけ）
           ある → タイトル「商品名 | Shop」、説明=商品説明の先頭、画像=image_urls[0]
           無い → _not_found_meta()
    except（DB の読み取りエラー）→ ログに出し、サイト共通の値（noindex なし）
    4. STATIC_PAGES にある → その値（/events?page=past は「Past Events」。/ は Organization を追加）
    5. それ以外 → _not_found_meta()（noindex あり・canonical なし）
```

### DB の読み取り（メモリキャッシュ付き）

| 関数 | 読む先 | クライアント | 条件 |
|---|---|---|---|
| `_fetch_event(key)` | `events`（`id, slug, name, start_date, end_date, time, location, address, page_content, daily_times`。管理情報は読まない）と `event_images`（表示順） | `supabase`（anon） | slug で探し、無ければ UUID の形のときだけ id で探す |
| `_fetch_article(id)` | `articles`（`id, title, content, image_urls, published_at, created_at`） | `admin_supabase` | UUID の形・`is_published = true`（公開 API と同じ） |
| `_fetch_product(id)` | `products`（`id, name, description, image_urls, created_at`） | `admin_supabase` | UUID の形・`is_published = true` |

- UUID の形でない文字列で id 列を検索すると DB がエラーを返すので、先に `_UUID_RE` で確かめる
- 結果は `_TTLCache`（スレッドセーフ。`threading.Lock`）に 60 秒覚える。「見つからなかった」ことも覚える。上限を超えたら期限切れを消し、それでも多ければ古い順に消す
- 画像の URL は `_absolute_url()` で絶対 URL にする（`/` 始まりは `SITE_ORIGIN` を付ける、`//` 始まりは `https:` を付ける、`blob:`・`data:` は使わない）

### タグの組み立て（render_head_tags）

- 値はすべて `html.escape(値, quote=True)` で `& < > " '` を文字参照にしてから入れる
- `twitter:card` はページ固有の画像があれば `summary_large_image`、無ければ `summary`
- 構造化データは `<script type="application/ld+json">` に入れる。`_json_for_script()` で `<`・`>`・`&`・U+2028・U+2029 を `\uXXXX` の形にして、`</script>` などで script が途中で閉じられないようにする

### イベントの構造化データ（_event_json_ld）

1. 開始日が読めなければ作らない
2. 開始日・終了日それぞれの時間帯の文字列を決める（`daily_times[その日]`、無ければ `time`）
3. 開始時刻は開始日の文字列の1つ目、終了時刻は終了日の文字列の2つ目。**両方そろったときだけ**両方を日時（`YYYY-MM-DDTHH:MM:00+09:00`）にし、どちらかが無ければ両方とも日付だけにする
4. 住所は `events.address`、無ければ `page_content.venue.address`。**どちらも無ければ作らない**（Google の必須項目 `location.address` を満たせないため）
5. `eventStatus` は `EventScheduled`、`eventAttendanceMode` は `OfflineEventAttendanceMode`、`organizer` は ei8ht plants、画像は最大5枚（無ければロゴ）

### robots.txt・sitemap.xml

- `robots_txt()`: `User-agent: *`・`Allow: /`・`ROBOTS_DISALLOW` の Disallow・`Sitemap:` 行を返す（`text/plain`）。`/api` は Disallow にしない（Google がページを描画するときに `/api/...` を読むため）
- `sitemap_xml()`: キャッシュに無ければ `_build_sitemap()` で作る。固定ページ → イベント（`supabase`。開始日の新しい順。slug、無ければ id）→ 公開中の記事（`admin_supabase`。lastmod は公開日、無ければ作成日）→ 公開中の商品（`admin_supabase`。lastmod は作成日）。どれかの読み取りに失敗しても読めた分だけ返し、そのときはキャッシュしない（`application/xml`）

```
GET /api/events/admin-info/dashboard（require_auth）
```

## 16. 画像・動画のアップロード（`routes/upload.py`、2026-10-22 変更）

`POST /api/upload`（画像）・`POST /api/upload/video`（動画）は、共通の `_store(file, 種類)` で次の順に処理する（管理者のみ）。

```
1. 申告された種類（Content-Type）を確かめ、拡張子を決める
     画像: image/jpeg→jpg・image/png→png・image/webp→webp・image/gif→gif
     動画: video/mp4→mp4・video/quicktime→mov・video/webm→webm・video/x-m4v→m4v
     どれでもない → 400（「jpeg / png / webp / gif のみ対応しています」など）
     ※ 利用者が付けたファイル名の拡張子は使わない
2. 上限 + 1 バイトまで読み、上限（画像 10MB・動画 500MB）を超えたら 400
3. ファイルの先頭のバイトで、中身が申告どおりの種類かを確かめる（違えば 400「ファイルの中身が形式と一致しません」）
     画像と偽った HTML などを公開の保存場所に置かれないようにするため
4. _ensure_bucket(バケット)  ← 下
5. 「新しい UUID.拡張子」の名前で置き（Cache-Control は 1 年）、公開 URL を返す
```

### バケットの確認（_ensure_bucket）

保存場所のバケット（`images`・`videos`）が無ければ作る。毎回作成を呼ぶと遅いので、確認できたバケットはプロセスの中で覚えておき、以後は呼ばない。

```
覚えている（確認済み）→ 何もしない
覚えていない → ロックの中で create_bucket(バケット, 公開) を呼ぶ
    成功 → 確認済みにする
    失敗 → 例外の文に「already exist」または「duplicate」が入っていれば、既にある扱いで確認済みにする
           それ以外（「does not exist」など）→ 確認済みにしない（次のアップロードでもう一度確かめる）。
                                             ログに例外の種類だけを1回だけ残す。アップロードはそのまま試す
```

- 2026-10-22 変更: それまではアップロードのたびに作成を呼び、失敗はすべて無視していた。確認できたバケットを覚えておくようにしたうえで、「既にある」とみなすのは「already exists」「duplicate」のときだけにした（ほかの失敗まで確認済みとして覚えると、本当にバケットが無いときに二度と作られないため）
