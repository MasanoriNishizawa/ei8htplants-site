## 1. 認証ガード（AdminLayout）

### 処理フロー

```
AdminLayout マウント
    │
    ├─ 開発用のログイン省略モード（SKIP_ADMIN_AUTH）? （2026-10-20 に判定を lib/devAuth.ts へ移した）
    │   YES → authed=true, checking=false（ログイン画面を出さない）
    │
    ├─ supabase が null ?
    │   YES → checking=false (未設定扱い)
    │   NO  → supabase.auth.getSession()
    │             │
    │             └─ session あり? → authed=true
    │                session なし? → authed=false
    │         checking=false
    │
    ├─ checking=true → null（空白）をレンダリング
    │
    ├─ authed=false → <LoginForm /> をレンダリング
    │   フォーム送信 (login関数)
    │     │
    │     ├─ supabase.auth.signInWithPassword({ email, password })
    │     │     │
    │     │     ├─ error → setError(error.message)
    │     │     └─ 成功  → setAuthed(true)
    │
    └─ authed=true → サイドバー + <Outlet />
        ログアウトボタン → supabase.auth.signOut() → setAuthed(false)
```

### 開発用のログイン省略モード（`lib/devAuth.ts`、2026-10-20 追加）

画面テスト（Playwright）で管理画面を開くための、開発中だけの仕組み。

- `SKIP_ADMIN_AUTH` は次の3つがすべてそろったときだけ true になる
  1. 開発サーバーで動いている（`import.meta.env.DEV`）
  2. モードが `production` ではない（`import.meta.env.MODE !== 'production'`）
  3. `VITE_SKIP_ADMIN_AUTH` が `'true'`（`npm run mock:e2e` で設定される）
- true のときにすること
  - `AdminLayout` はログイン画面を出さずに管理画面を表示する
  - `lib/api.ts` の認証つき呼び出し（`authRequest`・`upload`・`uploadVideo`）は、ログインしていなくてもダミーのトークン `dev-skip-admin-auth`（`DEV_SKIP_AUTH_TOKEN`）を付けて送る。これでテスト用のモック（MSW）までリクエストが届き、モックのデータが画面に出る
- 安全のための決まり
  - 本番ビルド（`npm run build`）では少なくとも 2 が満たされない（ビルド時に NODE_ENV=development が残っていて 1 が満たされる場合も含む）ので、`VITE_SKIP_ADMIN_AUTH` を何に設定しても働かない
  - 本物のバックエンドはダミーのトークンを受け付けず `401` を返す
  - 管理画面の「チャット Q&A」「チャットログ」は自分でセッションを読んでいるため、ダミーのトークンは使わない

```
lib/api.ts の getAccessToken()（authRequest・upload・uploadVideo が共通で使う）
    │
    ├─ Supabase のセッションがある → そのトークンを返す
    ├─ セッションが無く SKIP_ADMIN_AUTH=true → 'dev-skip-admin-auth' を返す
    └─ どちらでもない → 「401 Unauthorized」のエラー（送信しない）
```

```

  │                  │                    │
  │  mount           │                    │
  │─────────────────►│                    │
  │                  │ getSession()       │
  │                  │───────────────────►│

  │                  │ setAuthed/checking │

#### 前へ・次へボタンの位置（2026-10-20 修正）

前へ（❮）・次へ（❯）のボタンは、写真の入れ物（`position: relative`）の中に `position: absolute` で重ねて置く。縦の位置は次のとおり。

| 設定 | 意味 |
|---|---|
| `top: '50%'` | ボタンの上端を写真の高さのちょうど半分の位置に合わせる |
| `transform: 'translateY(-50%)'` | ボタン自身の高さの半分だけ上に戻す。これでボタンの中心が写真の上下の真ん中にそろう |

以前は `top: 40`（写真の上端から 40px）に固定されていたため、写真の高さが変わってもボタンは上のほうにあり、上寄りに見えていた。同じ書き方を次の3か所に入れている。

| ファイル | 使われている画面 | ボタンの大きさ |
|---|---|---|
| `components/EventPreview.tsx` | /events 一覧のカード、ホームの Next Event の大きいカード | 26px |
| `pages/EventSite.tsx` | イベント専用ページ `/events/:id`（写真は横幅いっぱい・高さは写真の縦横比どおり） | 30px |
| `components/EventCard.tsx` | 現在どの画面からも使われていない（自動テストからだけ読み込み） | 32px |

画面テスト `frontend/e2e/event-image-arrows.spec.ts`（E2E-N）で、スマホ幅とパソコン幅の両方について、ボタンの縦の中心が写真の縦の中心と ±2px 以内でそろうことを確かめている。

ライトボックスは共通部品 `components/ImageLightbox.tsx`（`EventPreview.tsx`・`EventCard.tsx`・`EventSite.tsx` で使用）。閉じ方は「✕ ボタン」「画像の外側（黒い背景）を押す」「Esc キー」の3つ。✕ ボタンを押したときは、押したことが外側の背景に伝わらないようにしてから閉じる（2026-10-20 修正。以前は ✕ を押すと閉じる処理が2回動いていた）。

## 8. WS予約フォーム URLパラメータ連携（Reserve.tsx）

### 処理フロー

```
URLパラメータ: ?event_id=<uuid>

useEffect #1 — イベント取得（[eventId] 依存）:
    api.events.get(eventId) → setEvent(event)
    単日イベントの場合: setForm(prev => ({...prev, preferred_date: start_date}))
    複数日イベントの場合: 日付ラジオを表示（preferred_date は未選択）

useEffect #2 — セッション取得（[event, form.preferred_date] 依存）:
    event.has_workshop かつ preferred_date が確定した場合のみ実行
    setSessions([])  ← 前の結果をクリア
    api.events.getSessions(eventId, form.preferred_date) → setSessions(data)
    // preferred_date を渡すことで、その日の予約数を反映した reserved_count を取得

セッション選択後:
    setForm(prev => ({...prev, session_id: session.id}))
    参加人数セレクトを有効化（1〜残席数）

送信:
    api.reserve.create(form)
    成功 → status='done'
    409  → status='full'（「このセッションは満席になりました」表示）
```

### 2-useEffect 分割の理由

- #1 と #2 を1つにまとめると、日付を変えるたびにイベント再取得が走る。
- 日付変更→セッション再ロード → `setSessions([])` で前日の選択がリセットされる。
- 複数日イベントで1日目の混雑状況が2日目に漏れないよう、`?date=` パラメータで日付別集計を行う。

    │

    ├─ 422 → 「メッセージを送れませんでした。内容を短くするか、ページを開き直してください。」を追加（localOnly: true）
    ├─ その他の res.ok でない応答 → 下の「失敗」へ
    ├─ res.ok → data = await res.json()
    │     ├─ data.reply が文字列でない、または空白だけ
    │     │     → 「うまくお答えできませんでした。言い方を変えてもう一度お試しください。」を追加（localOnly: true）
    │     └─ それ以外 → setMessages([...next, { role: 'model', content: data.reply }])
    │
    └─ 失敗  → 「申し訳ありません、エラーが発生しました。…」を追加（localOnly: true）
    │           （案内はすべて t() でバイリンガル対応）
    │
    ▼
setLoading(false)
```

入力欄（textarea）には `maxLength={MAX_MESSAGE_CHARS}`（2,000）を付けており、2,000 文字を超えて入力できない（2026-10-20 追加）。

### 送る会話の整え方（`lib/chatHistory.ts`、2026-10-20 追加）

サーバー（`POST /api/chat`）の入力チェックに合わない会話を送ると `422` になるため、送る前に整える。

| 名前 | 内容 |
|---|---|
| `MAX_SEND_MESSAGES` | 送る会話の最大件数 = 40（サーバーの `MAX_MESSAGES` と同じ） |
| `MAX_MESSAGE_CHARS` | 1件の本文の最大文字数 = 2,000（サーバーの `MAX_MESSAGE_CHARS` と同じ。入力欄の上限にも使う） |
| `clampContent(content)` | 本文を 2,000 文字までに切る。絵文字なども 1 文字として数え（`Array.from` で分ける）、途中で壊れた文字にしない |
| `toSendHistory(history)` | 画面の会話から送る会話を作る（下の手順） |

`toSendHistory` の手順:

```
1. localOnly の案内・本文が空白だけのもの・本文が文字列でないものを外す
2. 利用者の発言のうち、すぐ後に AI の返事が無いものを外す（最後の 1 件 = 今回の質問は残す）
   → 利用者と AI の発言が交互になり、最後は今回の質問になる
3. 新しいほうから 40 件だけにする
4. 各本文を clampContent で 2,000 文字までに切り、{ role, content } だけにする（localOnly の印は送らない）
```

例: 「挨拶 → 質問a → エラーの案内（localOnly）→ 質問b」なら、送るのは「挨拶 → 質問b」。

- 管理情報を保存すると、収支の出店料・宿泊費も管理情報の値（出店料・宿泊料金）に合わせて保存する。空欄なら 0 にする

- `toFinanceBody(fin)`: 収支の取得結果から、保存 API に送る 12 項目（sales・booth_fee・distance・gas_price・expressway_toll・accommodation・ws_participants・payment_flag・ws_payment_done・other_expenses・other_expenses_note・notes）だけを取り出す。`id`・`event_id`・`updated_at` は送らない。`payment_flag`・`ws_payment_done` が null（古いデータ）のときは false で補う（そのまま送るとサーバーの入力チェックで弾かれるため）

- 残る制約: 収支画面と管理情報の編集画面を同時に開いたまま、別々に保存すると、出店料・宿泊費は最後に保存した画面の値になる（2つの画面で同じ値を互いに書き合う仕組みのため）。ほかの項目は消えない

- 画面内の値（state ではない）: `viewFrom`（確認画面に来る前の画面。`location.state.from`）、`viewPath`（確認画面の URL）、`isDirty`（未保存の変更があるか。上の処理フローを参照）

- 受け取る `location.state.from`（確認画面に来る前の画面）は使わずに持っておき、確認画面へ戻るときにそのまま渡す。これで確認画面の「← 戻る」が元の画面（イベント一覧など）に戻れる

             setLoadFailed(true)（2026-10-16 追加）
finally → setLoading(false)
```

### 保存時の処理（save）

```
0. loadFailed が true なら何もせず終わる（2026-10-16 追加。保存ボタンも押せない）
1. await api.events.saveFinances(id, form)
2. latestAdminInfo = await api.events.getAdminInfo(id)   ← 保存の直前に管理情報の最新を取り直す（2026-10-16 変更）
3. await api.events.saveAdminInfo(id, { ...latestAdminInfo, booth_fee: 出店料, hotel_fee: 宿泊費 })
4. 成功 → 遷移元（収支一覧またはイベント一覧）へ戻る
   失敗 → setError('保存に失敗しました。もう一度お試しください。')、画面に留まる（保存ボタンはもう一度押せる）
   ※ 2 の取り直しに失敗した場合は 3 を行わない。1 の収支の保存は済んでいるので、もう一度保存すれば管理情報にも反映される
```

| state | 型 | 説明 |
|---|---|---|
| `loadFailed` | `boolean` | 読み込み（イベント・収支・予約・管理情報）が1つでも失敗したとき true。true の間は保存ボタンを押せず（薄く表示）、保存処理も先頭で止める（2026-10-16 追加） |

- 読み込みに失敗した画面では、そもそも保存できない（2026-10-16 変更）。初期値（金額 0 など）のまま保存して既存の収支を上書きしたり、空の管理情報で搬入・宿泊・出店要項などを消したりしないため
- 2026-10-16 より前は、管理情報を読み込めていないときに空の初期値をもとに管理情報を保存していたため、入力済みの内容が消えるおそれがあった
- 管理情報に同期するのは出店料・宿泊費だけ。搬入・宿泊ホテル名・出店要項などは、保存の直前に取り直した最新の管理情報の値をそのまま使う（2026-10-16 変更）
- 2026-10-16 の上の変更より前は、画面を開いた時点で読み込んだ管理情報（`adminInfo`）に出店料・宿泊費だけ差し替えて保存していた。そのため、画面を開いた後に管理情報の編集画面で保存した搬入・出店要項などを古い内容で上書きして消していた
- 残る制約: 収支画面と管理情報の編集画面を同時に開いたまま、別々に保存すると、出店料・宿泊費は最後に保存した画面の値になる（2つの画面で同じ値を互いに書き合う仕組みのため）。ほかの項目は消えない
- 管理情報の画面から保存したときは、反対に出店料・宿泊料金が収支に同期される（15節）

## 18. アクセス解析 — GA4 のページビュー送信（Analytics.tsx、2026-10-16 追加）

### 実装ファイル
- `frontend/src/lib/analytics.ts` — 有効判定・タグ（gtag.js）の読み込み・ページビュー送信・管理者のログイン判定と送信停止（2026-10-17 追加）
- `frontend/src/components/Analytics.tsx` — 画面遷移を見てページビューを送るコンポーネント（何も描画しない）
- 置き場所: 公開ページのレイアウト `Layout.tsx`・`StoreLayout.tsx` の先頭。管理画面のレイアウト（`AdminLayout`）には置かない

### 処理フロー

```
Analytics（pathname・search が変わるたびに useEffect）
1. isAnalyticsEnabled(location.hostname, import.meta.env.PROD) が false なら何もしない
   → 本番ビルドかつ ei8htplants.com / www.ei8htplants.com のときだけ true
   → 開発サーバー・Vitest・Playwright・Render の `*.onrender.com` の URL ではタグを読み込まず、外部送信もしない
1-2. 管理画面にログインしているブラウザか確かめる（2026-10-17 追加）
   isAdmin = hasAdminSession(window.localStorage)
   ※ window.localStorage を読むだけで例外が出る環境（Cookie を全てブロックしているなど）では
     try で受け止めて isAdmin = false（一般の訪問者として扱い、公開ページを止めない）
1-3. setAnalyticsDisabled(isAdmin)
   → window['ga-disable-G-HCVVDNYL94'] = isAdmin（Google 公式の送信停止の仕組み）
   isAdmin が true ならここで終わり（タグの読み込みもページビューの送信もしない）
2. loadGtag()（初回だけ）
   - window.dataLayer と window.gtag を用意し、gtag('config', 'G-HCVVDNYL94', { send_page_view: false })
   - config の page_location にも、秘密のクエリを外した今の URL を入れる
   - gtag.js を <script async> で読み込む
3. trackPageView(pathname, search, document.title)
   - isExcludedPath（/admin と /admin/〜）なら送らない
   - sanitizeSearch(search) で、送ってよいクエリだけを残す
   - gtag('set', { page_location })  ← GA が自動で送るスクロール・クリックなどにも同じ URL を使わせる
   - gtag('event', 'page_view', { page_location, page_path, page_title })
```

- SPA なので、GA の自動ページビュー（`send_page_view`）は止め、画面遷移のたびに自分で送る
- ページタイトルは各ページの `PageMeta`（React 19 の `<title>`）が画面確定時に反映済みなので、`document.title` をそのまま使う
  - ただし、データを読み込んでから `PageMeta` を出すページ（イベント詳細 `EventSite`・記事 `JournalArticle`・商品 `ShopProduct`）は、送る時点ではまだ題名が決まっていないため、page_title がサイト名（ei8ht plants）になる。GA ではパス（page_path）で集計できるので、そのままにしている
- **送ってよい URL のクエリは `page`（/events の過去イベント切り替え）・`event_id`（/reserve）・`utm_〜`（流入元の識別）だけ**。それ以外は外して送る
  - 予約キャンセルの URL（`/cancel?id=トークン`）のトークンがあると予約を取り消せるため、GA に残さない
  - ページで新しいクエリを使うときは、秘密の値でなければ `analytics.ts` の `ALLOWED_QUERY_KEYS` に足す
- **GA の管理画面で「拡張計測機能 → ページの変更（ブラウザの履歴イベントに基づく）」をオフにすること**。オンのままだと、GA 側の自動送信と二重に数えられる
- 測定 ID は公開してよい値なのでコードに直接書いている（秘密情報ではない）

### 管理者自身の閲覧を数えない（2026-10-17 追加）

管理画面（/admin）は以前から計測していない。それに加えて、管理画面にログインしているブラウザで公開サイトを見たときも GA4 に送らない。

| 関数（analytics.ts） | 動き |
|---|---|
| `hasAdminSession(storage)` | ブラウザの保存領域（localStorage）に、Supabase のログイン情報（キー名が `sb-<プロジェクト>-auth-token` の形で、値が空でないもの）があれば true。キーがあるかと値が空でないかだけを確かめ、ログイン情報の中身（トークンなど）を解析したり使ったりはしない。`-code-verifier` が付いたキーや、プロジェクト名の部分が空のキー（`sb--auth-token`）は対象外。保存領域が使えないとき（エラーになるとき）は false |
| `setAnalyticsDisabled(disabled)` | `window['ga-disable-G-HCVVDNYL94']` に true / false を入れる。Google 公式の送信停止の仕組みで、ページビューだけでなく、タグを読み込んだ後に GA が自動で送るスクロール・クリックなどの計測も止まる |

- 画面が切り替わるたびにログイン情報を確かめるので、公開サイトを見ている途中で管理画面にログインすると、その後の閲覧は送らない。ログアウトすると（Supabase がログイン情報を消すので）次の画面から送信を再開する
- 本番サイト以外では、ログインの確認もしない（1. の時点で終わる）
- 注意（運用）:
  - ei8htplants.com と www.ei8htplants.com はブラウザの保存領域が別。管理画面にログインしている方のドメインで見たときだけ数えなくなる（もう片方のドメインで見ると数えられる）
  - 管理画面にログインしていない端末（ログアウトしたスマホ、一度もログインしていない端末など）で見た分は、一般の訪問者と同じように数えられる

### 表示の決め方

| 表示 | 決め方 |

| 未入力 | 文字の項目は、空・null・空白と改行だけのとき「未入力」（`hasText()` で判定）。数値は null のとき |

| 各項目の並び | 項目名（幅 120px）と値を横に並べ、幅が足りないとき（スマホなど）は値が項目名の下に回る（`flex-wrap`） |

### 表示と動き

```
NAV_ITEMS を順に描く
  ├─ 'group' がある → 見出し
  ├─ 'href' がある → <a href={href} target="_blank" rel="noopener noreferrer">

- 未ログインのときはメニュー自体を出さないので、「分析 ↗」も出ない
- 分析ダッシュボードのログインは別に行う（管理画面のログイン状態は渡さない）
