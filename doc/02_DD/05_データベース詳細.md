### event_admin_info（016マイグレーション、2026-10-16 追加）

イベントの管理情報（搬入・搬出・宿泊・出店料・出店要項など、管理者だけが見る情報）を入れる専用テーブル。1つのイベントにつき1行。

**作った理由**: 以前は events テーブルの `admin_info` 列に入れていた。events テーブルはサイトにイベントを表示するため、ログインしていない人でも全列を読める設定になっている。そのため、サイトの画面には出していなくても、Supabase に直接問い合わせると管理情報まで読めてしまう状態だった。ログインしていない人には読めないこのテーブルに移して対策した（017 の実行で完了）。017 を実行するまでは events の `admin_info` 列に古い管理情報が残り、未ログインでも Supabase に直接問い合わせると読める。対策が完了するのは 017 の実行後。

```sql
CREATE TABLE IF NOT EXISTS event_admin_info (
  event_id   uuid PRIMARY KEY REFERENCES events(id) ON DELETE CASCADE,
  info       jsonb NOT NULL DEFAULT '{}'::jsonb,
  updated_at timestamptz NOT NULL DEFAULT now()
);
```

| 列 | 内容 |
|---|---|
| `event_id` | 対象のイベント。1イベントにつき1行だけ。イベントを削除すると、この行も一緒に削除される |
| `info` | 管理情報の中身。項目は上の「管理情報の中身」と同じ |
| `updated_at` | 最後に保存した日時。管理画面から保存するたびにサーバーが書き込む |

- 読み書きできるのはサーバー（`service_role`）だけ。ログインしていない人（`anon`）・ログイン済みの利用者（`authenticated`）からは読めない（「4. Row Level Security」の節を参照）
- 管理情報をまだ保存していないイベントには行がない。この場合、管理情報の取得 API は空の `{}` を返す
- 016 を実行したとき、events の `admin_info` に入っていた管理情報（空でないもの）をこのテーブルに写している

**移行期間中の自動の写し（トリガー）**: 016 を実行してから新しいサーバーのプログラムに切り替わるまでの間は、古いプログラムがまだ events の `admin_info` に書き込む。その内容を取りこぼさないよう、016 で次の仕組みを入れている。

- 関数 `sync_event_admin_info_from_events` とトリガー `trg_sync_event_admin_info`: events にイベントを追加したとき、または `admin_info` を書き換えたときに、その内容（空でない場合だけ）を `event_admin_info` に写す。すでに行があれば後から書いた内容で上書きする
- 017 マイグレーションで、このトリガーと関数は削除する

**移行手順**（016・018・017 の実行順。[移行計画書 5章](../05_OP/01_移行計画書.md) にも同じ内容を記載）:

1. Supabase の SQL エディタで `016_event_admin_info.sql` を実行する
2. 続けて `018_grant_event_admin_info.sql` を実行する（サーバーに読み書きの権限を付ける。デプロイより前に行う。2026-10-16 追加）
3. 新しいプログラムをデプロイする（`main` へのプッシュで Render が自動で反映）。反映後、管理画面でイベントの「管理情報」を開き、登録済みの内容が表示されることを確認する
4. Supabase の SQL エディタで `017_drop_events_admin_info.sql` を実行する

1〜4 は、管理画面で管理情報や収支を保存しない時間帯に続けて行うのが望ましい（収支画面の保存でも管理情報（出店料・宿泊費）が書き込まれるため）。途中で保存しても、トリガーと 017 の再写しで取りこぼしは防いでいる。

在庫アトミック減算関数:
```sql
CREATE OR REPLACE FUNCTION decrement_stock(p_product_id uuid, p_quantity integer)
RETURNS boolean LANGUAGE plpgsql AS $$
DECLARE updated integer;
BEGIN
    UPDATE products SET stock = stock - p_quantity
    WHERE id = p_product_id AND stock >= p_quantity;
    GET DIAGNOSTICS updated = ROW_COUNT;
    RETURN updated > 0;
END;
$$;
```

## 4. Row Level Security (RLS) ポリシー

### events / event_images

```sql
ALTER TABLE events ENABLE ROW LEVEL SECURITY;
CREATE POLICY "public read events" ON events FOR SELECT TO anon USING (true);
CREATE POLICY "service write events" ON events FOR ALL TO service_role USING (true);
```

- `public read events` は列を限定していないため、未ログイン（`anon`）でも Supabase に直接問い合わせると events の全列を読める。以前はここに管理者専用の `admin_info` 列があり、管理情報まで読めてしまう状態だった
- 2026-10-16 対策済み（017 の実行で完了）: 管理情報は専用テーブル `event_admin_info` に移した（下の節を参照）。events の `admin_info` 列は 017 マイグレーションで削除する。017 を実行するまでは古い列が残るため、公開 API（FastAPI）の応答からは引き続き `admin_info` を取り除いている。017 を実行するまでは events の `admin_info` 列に古い管理情報が残り、未ログインでも Supabase に直接問い合わせると読める。対策が完了するのは 017 の実行後

### event_admin_info（016マイグレーション）

```sql
ALTER TABLE event_admin_info ENABLE ROW LEVEL SECURITY;
CREATE POLICY "service_role_all" ON event_admin_info
    FOR ALL TO service_role USING (true) WITH CHECK (true);
-- 念のため、Supabase が新しいテーブルに自動で付ける権限も取り消す
REVOKE ALL ON event_admin_info FROM anon, authenticated;

-- 018マイグレーション（2026-10-16 追加）: サーバーに読み書きの権限を付ける
GRANT SELECT, INSERT, UPDATE, DELETE ON event_admin_info TO service_role;
```

- サーバー（`service_role`）だけが読み書きできる。未ログイン（`anon`）・ログイン済みの利用者（`authenticated`）向けの許可は作っていないので、どちらも読めない
- さらに `anon`・`authenticated` の権限そのものも取り消している。万一 RLS（行ごとのアクセス制限）が無効にされても読めないようにする二重の守り
- サーバーが読み書きするには、上の許可（ポリシー）に加えて、テーブルそのものへの権限（GRANT）も必要。このプロジェクトでは新しいテーブルを作っても `service_role` の権限が自動で付かなかったため、018 で付けている。`anon`・`authenticated` には付けない
- 2026-10-16 の経緯: 016 の実行とデプロイの後、権限が無かったため管理情報の取得・保存が失敗し（`permission denied for table event_admin_info`）、管理情報ページが「データの読み込みに失敗しました」になった。018 と同じ SQL を実行して解消した。新しい環境で作り直すときは、016 の後に 018 も実行する

同様に `anon` SELECT 可、`service_role` 全操作可。

## 5. データ型・制約の補足

| カラム | 型 | 補足 |
|---|---|---|
| `id` | UUID | `gen_random_uuid()` でランダムUUID v4 |
| `brands` (events/stockists) | `TEXT[]` | PostgreSQL配列型。空配列は `'{}'` |
| `page_content` (events) | `JSONB` | イベント専用サイトのコンテンツ（hero / venue / lineup 等） |
| `daily_times` (events) | `JSONB` | 日付 → 時間帯のマップ `{"2025-10-01": "11:00〜17:00"}` |
| `admin_info` (events) | `JSONB` | 旧：管理者専用の運営情報（搬入・搬出日時、宿泊ホテル、出店料、出店要項など）。2026-10-16 に `event_admin_info.info` へ移し、017 マイグレーションで列ごと削除する。017 実行までは列が残るため、公開 API（FastAPI。`GET /api/events`・`GET /api/events/{id}`）の応答からは除いている。2026-10-16 より前は公開 API の応答にも含まれていた |
| `info` (event_admin_info) | `JSONB NOT NULL DEFAULT '{}'` | 管理者専用の運営情報（搬入・搬出日時、宿泊ホテル、出店料、出店要項など）。2026-10-16 追加。未ログインでは読めない。管理情報を保存していないイベントは行自体がない |
| `status` (workshop_reservations) | `TEXT` | CHECK制約なし。実質的な値は `pending` / `cancelled`（`confirmed` は後方互換エイリアス） |
| `cancel_token` (workshop_reservations) | `TEXT` | 8桁ランダム数字。予約作成時に生成・以降不変。受付メールにキャンセルリンクとして含まれる |
| `lang` (workshop_reservations) | `TEXT` | `'ja'` または `'en'`。受付メールの言語を決定。NULL の場合は日本語扱い |
| `reserved_count` (ws_sessions) | `INTEGER` | デノーマライズ値。`_sync_reserved_count()` で同期、`GET /sessions` でライブ値に上書き |
| `is_read` (contacts) | `BOOLEAN NOT NULL DEFAULT false` | NULL不可。デフォルト未読 |
| `display_order` (各テーブル) | `INTEGER NOT NULL DEFAULT 0` | INSERT時にアプリ層でcount+1を付与 |

マイグレーションは Supabase SQLエディタで手動実行する（CLI管理なし）。  
`CREATE TABLE IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS` を使用しており、冪等に実行可能（何度実行しても同じ結果になる）。ただし `017_drop_events_admin_info.sql` は例外で、1 回だけ実行する（2 回目以降は削除済みの列を読もうとして失敗するが、全体が取り消されるので害はない）。

**マイグレーションファイルに含まれない手動適用変更:**

```sql
ALTER TABLE ws_sessions
    ADD COLUMN IF NOT EXISTS reserved_count INTEGER NOT NULL DEFAULT 0;

ALTER TABLE workshop_reservations
    ADD COLUMN IF NOT EXISTS cancel_token TEXT;

ALTER TABLE workshop_reservations
    ADD COLUMN IF NOT EXISTS lang TEXT;

CREATE INDEX IF NOT EXISTS idx_reservations_cancel_token
    ON workshop_reservations (cancel_token);

-- 2026-10-15 追加: イベント管理情報（搬入・搬出・宿泊・出店料）
-- 2026-10-16: event_admin_info テーブルへ移した。017 マイグレーションでこの列は削除する
ALTER TABLE events
    ADD COLUMN IF NOT EXISTS admin_info JSONB;
```
