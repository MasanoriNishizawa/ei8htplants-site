`slug`（URL スラッグ）: マイグレーションの SQL には無い（手で追加した列）。イベントの編集画面で入れると、イベントのページを `/events/スラッグ` で開ける。`GET /api/events/{id}` はスラッグで先に探し、無ければ ID で探す。空で保存すると `NULL`。型・重複を禁止する制約があるかは SQL ファイルが無いため確かめられていない（コードは `.eq('slug', …)` で1件目を使う）。

> 2026-10-16 変更: 管理情報（`admin_info`）は events テーブルから専用テーブル `event_admin_info` に移した（下の「event_admin_info」の節を参照）。events の `admin_info` 列は 017 マイグレーションを実行した時点で削除される。017 を実行するまでは列が残るが、サーバーはもう読み書きしない。017 を実行するまでは events の `admin_info` 列に古い管理情報が残り、未ログインでも Supabase に直接問い合わせると読める。対策が完了するのは 017 の実行後。

### event_admin_info（016マイグレーション、2026-10-16 追加）

イベントの管理情報（搬入・搬出・宿泊・出店料・出店要項など、管理者だけが見る情報）を入れる専用テーブル。1つのイベントにつき1行。

**作った理由**: 以前は events テーブルの `admin_info` 列に入れていた。events テーブルはサイトにイベントを表示するため、ログインしていない人でも全列を読める設定になっている。そのため、サイトの画面には出していなくても、Supabase に直接問い合わせると管理情報まで読めてしまう状態だった。ログインしていない人には読めないこのテーブルに移して対策した（017 の実行で完了）。017 を実行するまでは events の `admin_info` 列に古い管理情報が残り、未ログインでも Supabase に直接問い合わせると読める。対策が完了するのは 017 の実行後。

```sql
CREATE TABLE IF NOT EXISTS event_admin_info (
  event_id   uuid PRIMARY KEY REFERENCES events(id) ON DELETE CASCADE,
  info       jsonb NOT NULL DEFAULT '{}'::jsonb,
  updated_at timestamptz NOT NULL DEFAULT now()
);
```

| 列 | 内容 |
|---|---|
| `event_id` | 対象のイベント。1イベントにつき1行だけ。イベントを削除すると、この行も一緒に削除される |
| `info` | 管理情報の中身。項目は上の「管理情報の中身」と同じ |
| `updated_at` | 最後に保存した日時。管理画面から保存するたびにサーバーが書き込む |

- 読み書きできるのはサーバー（`service_role`）だけ。ログインしていない人（`anon`）・ログイン済みの利用者（`authenticated`）からは読めない（「4. Row Level Security」の節を参照）
- 管理情報をまだ保存していないイベントには行がない。この場合、管理情報の取得 API は空の `{}` を返す
- 016 を実行したとき、events の `admin_info` に入っていた管理情報（空でないもの）をこのテーブルに写している

**移行期間中の自動の写し（トリガー）**: 016 を実行してから新しいサーバーのプログラムに切り替わるまでの間は、古いプログラムがまだ events の `admin_info` に書き込む。その内容を取りこぼさないよう、016 で次の仕組みを入れている。

- 関数 `sync_event_admin_info_from_events` とトリガー `trg_sync_event_admin_info`: events にイベントを追加したとき、または `admin_info` を書き換えたときに、その内容（空でない場合だけ）を `event_admin_info` に写す。すでに行があれば後から書いた内容で上書きする
- 017 マイグレーションで、このトリガーと関数は削除する

**移行手順**（016・018・017 の実行順。[移行計画書 5章](../05_OP/01_移行計画書.md) にも同じ内容を記載）:

1. Supabase の SQL エディタで `016_event_admin_info.sql` を実行する
2. 続けて `018_grant_event_admin_info.sql` を実行する（サーバーに読み書きの権限を付ける。デプロイより前に行う。2026-10-16 追加）
3. 新しいプログラムをデプロイする（`main` へのプッシュで Render が自動で反映）。反映後、管理画面でイベントの「管理情報」を開き、登録済みの内容が表示されることを確認する
4. Supabase の SQL エディタで `017_drop_events_admin_info.sql` を実行する

1〜4 は、管理画面で管理情報や収支を保存しない時間帯に続けて行うのが望ましい（収支画面の保存でも管理情報（出店料・宿泊費）が書き込まれるため）。途中で保存しても、トリガーと 017 の再写しで取りこぼしは防いでいる。

サーバーの `reservation_policy.is_workshop_day` と同じ決まりを DB でも使う。実施する日なら true、それ以外は false（NULL は返さない。日付が NULL なら false）。

### 予約の確かめ（023 のトリガー `check_reservation_session`。2026-11-13 追加）

予約の追加と、予約の `session_id`・`preferred_date`・`status` の変更で動き、合わなければ保存させない。

**最初に止めるもの**（2026-11-13、4回目の修正）

- キャンセルからの戻しは、関数 `reinstate_reservation` の中（関数が目印 `app.reservation_reinstate = 'on'` を立てている間）でしか認めない。ほかの経路（状態だけの UPDATE で戻す）はロックを取る前に `P0414` で止める（満席の確認のすり抜けと行き詰まりを防ぐ）。サーバーは `409`「予約の状態が変わりました。画面を読み込み直してください」にする（アプリはふつう出さない）

**確かめないもの**

- 新しい状態がキャンセル（キャンセルにする・キャンセルのままの変更）
- 枠・予約日が変わらない、キャンセル以外どうしの状態の変更（`pending` → `confirmed` など。前からある食い違った古いデータで状態の変更が止まらないように）
- 枠を消したときの SET NULL（枠だけが空になる変更）
- 枠の付け替え（予約日は変えず、別の枠を指すようにする変更。日程の保存の手順6）では、実施日の確認と「枠なしなのにその日に枠がある」の確認だけを省く（日程の保存の付け替えが古いデータで止まらないように）。同じイベントの枠か・日付が合うか（下の表の 5・6、`P0411`・`P0410`）は確かめる

**確かめる順番**（予約の追加・キャンセルからの戻し・予約日の変更のとき）

| 順 | すること | 合わないときの例外 | サーバーの応答 |
|---|---|---|---|
| 1 | イベントの行を共有ロック（`FOR SHARE`）で取る | — | — |
| 2 | ワークショップのあるイベントで、予約日が実施する日か（`ws_is_workshop_day`。枠の有無にかかわらず。予約日が空の古い予約は確かめない） | `P0412` | `400`「この日はワークショップを実施していません」 |
| 3 | 予約の追加・キャンセルからの戻しで、時間枠なしなのに、その日に使える枠が無いか（当日参加 `is_walkin` は通す。枠の付け替えでは確かめない）。2026-11-13、4回目の修正で追加 | `P0411`（`reservation_session_required`） | 予約は `400`「時間枠を選んでください」（確かめたあとで管理者がその日に枠を足した直後に起きることがある）、キャンセルからの戻しは `400`「ワークショップの時間枠が正しくありません」 |
| 4 | 枠の無い予約はここで終わる。枠があれば、枠の行を共有ロックで取る | — | — |
| 5 | 枠があり、予約と同じイベントの枠か | `P0411` | `400`（予約は「ワークショップの時間枠が正しくありません」、当日参加は「イベントまたは時間枠が正しくありません」） |
| 6 | 日付のある枠なら、予約日がその日か（予約日が空も不可） | `P0410` | `400`「この時間枠は選んだ日には使えません」 |

- 先に枠なしで受け付けた予約は、あとから同じ日に枠が足されてもそのまま残る（日程の保存は枠なし・時間なしの予約を付け替えずに残す。止めるのは新しい追加と戻しだけ）

- 「イベント → 枠」の順でロックを取る。日程の保存（下の関数。イベントを `FOR NO KEY UPDATE` で取る）とぶつかるので、日程の保存と予約の保存が重なっても1つずつ通る。日程の保存が先なら、予約はそれを待ってから新しい実施日で確かめる（このときに `P0412` で止まることがある）。予約が先なら、日程の保存はそれを待ってからその予約を見て `P0409` にする
- 関数の実行権限は anon・authenticated から取り消している

### 日程の保存（023 の関数 `save_event_schedule(p_event_id, p_event, p_sessions)`。2026-11-13 追加）

イベント本体と時間枠を1つのトランザクションで保存し、キャンセル以外の予約を確かめて新しい枠へ付け替える。途中で例外が出たら全部が取り消される（イベント本体・時間枠・予約の付け替えのどれも残らない）。サーバー（service_role）だけが呼べる。

| 引数 | 中身 |
|---|---|
| `p_event_id` | 対象イベントの ID。NULL ならイベントを新しく作る |
| `p_event` | イベント本体の列（JSON。サーバーが確かめて整えたもの）。NULL ならイベント本体は変えない。キー `ws_dates` が無ければ、`ws_dates` は今の値のまま |
| `p_sessions` | 時間枠の一覧（JSON の配列。`{id?, time_label, max_participants, session_date}`。並びが表示順）。NULL なら今の枠をそのまま入力として扱い、日付の確認と予約の確認・付け替えまで行う |
| 戻り値 | イベントの ID |

流れ:

1. 更新なら、保存前のイベントの行をロック（`FOR NO KEY UPDATE`）して控える（無ければ `P0404`）。イベントを作る・更新する（`p_event` があるとき）
2. 保存後のイベントの行を読み直す
3. 保存後の実施日を確かめる。空の配列は `P0422`「実施日を1日以上選んでください」、開催期間の外の日は `P0422`「ワークショップの実施日が開催期間の外です」
4. 既存の時間枠をロック（`FOR UPDATE`）し、保存前の表示名・日付を控える。`p_sessions` が NULL なら今の枠を入力にする。入力の枠の日付を確かめる（実施日のあるイベントは実施日のどれか、無いイベントは NULL）。違えば `P0422`。今の枠を入力にしたとき（`p_sessions` が NULL）は「時間枠の日付がワークショップの実施日と合わなくなります。時間枠も一緒に保存してください」
5. 入力の順に、既存の枠は更新・新しい枠は作成する（突き合わせは、`id` が既存の枠にあればその枠、無ければ表示名と日付が同じ既存の枠）
6. キャンセル以外の予約すべてを確かめ、保存後の枠へ付け替える
   - まず予約日が保存後も実施する日か（`ws_is_workshop_day`）を確かめる。保存前は実施する日だったのに、実施しない日になったら移し先なし。実施日から外す・開催期間を縮める・ワークショップをなしにする、のどれでも同じ。保存前から実施しない日だった古い予約（前からある食い違ったデータ）は、日付では止めない
   - 枠を指しておらず希望の時間も無い予約（枠0件の日の予約）は、そのまま残す
   - 今の枠が残り、予約日に使えるならそのまま
   - そうでなければ、表示名（今の枠の保存前の表示名か、予約の `preferred_time`）が同じで予約日に使える枠へ移す（その日だけの枠を、全日程で共通の枠より先に選ぶ）。移した予約は `preferred_time` も移し先の表示名にそろえる
   - 移し先が無い予約があれば、日時ごとにまとめて `P0409` を出す（DETAIL に `[{date, time_label, count, participants}]` の JSON。`time_label` は時間の指定の無い予約では null）。何も保存しない。枠を指していない古い予約は、保存前にどの枠にも数えられていなかったもの（古い自由入力の時間など）ならそのまま残す
7. 送られなかった枠を消す
8. 枠ごとの予約済みの人数（`reserved_count`）を数え直す

例外の SQLSTATE とサーバーの応答: `P0404` → `404`、`P0422` → `422`（関数の文言のまま）、`P0409` → `409`（[DD-06](06_API仕様.md)）。

### キャンセルからの戻し（023 の関数 `reinstate_reservation(p_reservation_id, p_status)`。2026-11-13 追加）

2026-11-13（4回目の修正）から、キャンセル以外への状態の変更全般を受け持つ（名前はそのまま）。ロックを取ったあとの状態がキャンセルでなければ状態だけを変え、キャンセルなら下の確かめをしてから戻す。戻すときは目印 `app.reservation_reinstate` を立てて UPDATE し、トリガーの `P0414` を通す。

キャンセルした予約を受付済（`pending`・`confirmed`）に戻す。サーバー（service_role）だけが呼べる。戻り値は更新後の予約の行（JSON）。

1. 予約を（ロックせずに）読み、イベントと枠の ID を知る（無ければ `P0404`）
2. イベントの行を共有ロックで取る（日程の保存と1つずつ通る）
3. 枠があれば、枠の行を共有ロックで取る
4. 予約の行をロック（`FOR UPDATE`）して読み直す。すでにキャンセルでなければ（同時に戻された）、状態だけを変えて返す。枠が消えていたら、枠の無い予約として確かめる
5. 確かめる（違えば例外を出し、何も変えない）

| 確かめること | 例外 | サーバーの応答 |
|---|---|---|
| ワークショップのあるイベントで、予約日が実施する日か | `P0412` | `400`「この日はワークショップを実施していません」 |
| 枠を指しているなら、枠があり同じイベントの枠か | `P0411` | `400`「ワークショップの時間枠が正しくありません」 |
| 枠を指していない（枠を消されたものも）なら、その日に使える枠が無いか（予約の API の「その日に枠があれば枠の指定が必須」と同じ決まり。当日参加 `is_walkin` は通す） | `P0411` | 同上 |
| 日付のある枠なら、予約日がその日か | `P0410` | `400`「この時間枠は選んだ日には使えません」 |
| 枠が満席でないか（アプリの満席の確認と同じ数え方: 同じイベントのキャンセル以外の予約で、予約日が同じもの（予約日が空なら全日程）のうち、その枠を指すもの、または枠を指さず希望の時間が枠の表示名と同じもの） | `P0413` | `409`「この時間枠は満席のため、キャンセルを取り消せません」 |
| 予約がある | `P0404` | `404` |

6. 状態を変えて、更新後の行を返す（トリガーももう一度確かめる）

- ロックの順番は「イベント → 枠 → 予約」（日程の保存・イベントの削除と同じ向き）。予約を先にロックしてからトリガーの中で枠を待つと、枠を消す日程の保存と互いに待って行き詰まるため、UPDATE の前にこの順でロックを取る

在庫アトミック減算関数（010 で作り、019 で数量の確認を足した）:
```sql
CREATE OR REPLACE FUNCTION decrement_stock(p_product_id uuid, p_quantity integer)
RETURNS boolean LANGUAGE plpgsql AS $$
DECLARE updated integer;
BEGIN
    -- 019 で追加: 数量が NULL・0 以下なら何もせず false（負の数で在庫が増えるのを防ぐ）
    IF p_quantity IS NULL OR p_quantity <= 0 THEN
        RETURN false;
    END IF;
    UPDATE products SET stock = stock - p_quantity
    WHERE id = p_product_id AND stock >= p_quantity;
    GET DIAGNOSTICS updated = ROW_COUNT;
    RETURN updated > 0;
END;
$$;
```

019 で、在庫の関数 `decrement_stock`・`increment_stock` を呼べるのはサーバー（service_role）だけにした（`PUBLIC`・`anon`・`authenticated` から実行の権限を取り消した）。それまでは公開の鍵（anon キー）で直接呼べた。`increment_stock` には数量の確認は無い（課題表 I-18）。

## 4. Row Level Security (RLS) ポリシー

### events / event_images

```sql
ALTER TABLE events ENABLE ROW LEVEL SECURITY;
CREATE POLICY "public read events" ON events FOR SELECT TO anon USING (true);
CREATE POLICY "service write events" ON events FOR ALL TO service_role USING (true);
```

- `public read events` は列を限定していないため、未ログイン（`anon`）でも Supabase に直接問い合わせると events の全列を読める。以前はここに管理者専用の `admin_info` 列があり、管理情報まで読めてしまう状態だった
- 2026-10-16 対策済み（017 の実行で完了）: 管理情報は専用テーブル `event_admin_info` に移した（下の節を参照）。events の `admin_info` 列は 017 マイグレーションで削除する。017 を実行するまでは古い列が残るため、公開 API（FastAPI）の応答からは引き続き `admin_info` を取り除いている。017 を実行するまでは events の `admin_info` 列に古い管理情報が残り、未ログインでも Supabase に直接問い合わせると読める。対策が完了するのは 017 の実行後

### event_admin_info（016マイグレーション）

```sql
ALTER TABLE event_admin_info ENABLE ROW LEVEL SECURITY;
CREATE POLICY "service_role_all" ON event_admin_info
    FOR ALL TO service_role USING (true) WITH CHECK (true);
-- 念のため、Supabase が新しいテーブルに自動で付ける権限も取り消す
REVOKE ALL ON event_admin_info FROM anon, authenticated;

-- 018マイグレーション（2026-10-16 追加）: サーバーに読み書きの権限を付ける
GRANT SELECT, INSERT, UPDATE, DELETE ON event_admin_info TO service_role;
```

- サーバー（`service_role`）だけが読み書きできる。未ログイン（`anon`）・ログイン済みの利用者（`authenticated`）向けの許可は作っていないので、どちらも読めない
- さらに `anon`・`authenticated` の権限そのものも取り消している。万一 RLS（行ごとのアクセス制限）が無効にされても読めないようにする二重の守り
- サーバーが読み書きするには、上の許可（ポリシー）に加えて、テーブルそのものへの権限（GRANT）も必要。このプロジェクトでは新しいテーブルを作っても `service_role` の権限が自動で付かなかったため、018 で付けている。`anon`・`authenticated` には付けない
- 2026-10-16 の経緯: 016 の実行とデプロイの後、権限が無かったため管理情報の取得・保存が失敗し（`permission denied for table event_admin_info`）、管理情報ページが「データの読み込みに失敗しました」になった。018 と同じ SQL を実行して解消した。新しい環境で作り直すときは、016 の後に 018 も実行する

### price_calc_entries（020マイグレーション、2026-10-24 追加）

```sql
ALTER TABLE price_calc_entries ENABLE ROW LEVEL SECURITY;
REVOKE ALL ON price_calc_entries FROM anon, authenticated;
GRANT SELECT, INSERT, DELETE ON price_calc_entries TO service_role;
```

- 許可（ポリシー）は作らない。RLS を有効にしているので、未ログイン（`anon`）・ログイン済みの利用者（`authenticated`）は読み書きできない。`anon`・`authenticated` の権限そのものも取り消している
- サーバー（`service_role`）は RLS を通らないので、許可が無くても読み書きできる。ただしテーブルそのものへの権限は要るので、読む・追加・削除（SELECT・INSERT・DELETE）を付けている（このプロジェクトの Supabase では新しいテーブルに自動で付かないことがある。018 と同じ理由）。書き換え（UPDATE）は API に無いので付けない
- 画面からは Supabase に直接つながず、サーバーの API（`/api/price-calc-entries`）だけを通す
