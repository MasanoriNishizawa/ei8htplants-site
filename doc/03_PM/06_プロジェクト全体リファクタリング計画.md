# PM-06 — プロジェクト全体リファクタリング計画

## 1. 目的と進め方

この計画は、既存機能の動作を保ちながら、テスト実行基盤と大きな責務を持つファイルを段階的に整理するためのものです。最初にテスト実行時の安全性と結果記録を整え、その後フロントエンド、バックエンドの順に進めます。

各段階は小さな変更に分け、変更対象に対応するテストを実行してから次へ進みます。予約・イベント・注文などデータ更新や外部サービス連携を含む処理は、失敗時の挙動を確認するテストが揃うまで分割に着手しません。画面/APIの仕様、URL、保存データ、SEO出力に意図しない変更がないことも確認します。

## 2. 段階と状態

| 段階 | 状態 | 対象 |
|---|---|---|
| 1. テストランナーとE2E実行の安全化 | 進行中 | `scripts/run_tests.py` の責務・実行結果判定・プロセス管理、Playwrightの起動と終了の隔離 |
| 2. フロントエンドの責務分割 | 進行中 | 重複 helper、API 型の配置、大きな画面コンポーネント |
| 3. バックエンドの分離準備 | 進行中 | SEO sitemap 生成処理の分離から着手。残りの SEO 処理、アプリ起動・ルーター登録と静的配信 |
| 4. 予約・イベント・注文の分割 | 未着手 | 失敗経路テストを先に整えたうえで、各処理を段階的に分離 |

未完了の範囲は、`run_tests.py` の各テスト起動・実行処理と結果解析の分離、起動失敗・途中中断時の確認、テストプロセス終了の確認です。ログの生成・追記とCLI引数に基づく実行対象の選択はそれぞれ別モジュールへ分離しましたが、段階1全体は未完了のため進行中とします。

対象はテスト実行基盤に限定します。サイトの画面、業務処理、API、データベース仕様は変更しません。

| 作業 | 完了条件 |
|---|---|
| `scripts/run_tests.py` の実行処理、結果の解析、実行結果の記録を見通しよく分ける | 各処理の入力と出力が明確で、実行経路が追える |
| 一部のテストを省略した実行を、全テスト成功として記録しない | `--no-e2e` を含め、省略・絞り込みがログ上で正しく区別される |

| E2E用サーバーとブラウザーの起動・終了をその実行に閉じる | 実行終了時に起動したプロセスを終了し、別用途のプロセスを一括終了しない |
| 結果判定・ログ出力・プロセス終了の確認を追加する | 成功、失敗、省略、起動失敗、途中終了を区別して確認できる |

このバッチまでに完了したのはログ生成・追記の分離、skip行判定、既存凡例の更新、単調時計の経過時間計測、CLI引数に基づく実行選択の分離、および関連テストの成功です。選択処理分離後の runner unittest 15件を含む全件 run は2026-10-28 03:32に成功しました。各テストの起動・実行処理と結果解析の分離、起動失敗・途中中断の検証、テストプロセス終了の確認は未完了です。

**主なリスク:** プロセス終了方法を誤ると、開発サーバーなどテスト以外のプロセスを停止するおそれがあります。また、結果判定の変更で実行ログの成功・失敗表示が変わる可能性があります。

**対策:** テストランナー自身が起動したプロセスだけを追跡して終了します。テスト対象を絞った実行、省略した実行、失敗した実行のそれぞれで結果表示を確認します。ログの形式を変える場合は、`doc/04_TEST/08_テスト実行ログ.md` との整合も確認します。

**段階の完了条件:** 関連するrunnerテストが成功し、テスト実行ログに実行範囲と省略項目が正しく記録されること。Playwright実行の終了後に無関係なプロセスが残る・停止する問題がないこと。コード変更後はリポジトリの作業手順に従って必要な型チェック、ビルド、関連テストを完了すること。

## 4. 第2段階 — フロントエンドの責務分割

この段階は進行中です。完了した範囲は次のとおりです。

- `Articles.tsx` と `Products.tsx` で重複していた本文画像 URL の抽出を `lib/blocks.ts` の `blockImageUrls(blocks)` に共通化しました。画像の順序を保ち、空 URL を除外した配列を記事・商品の保存データの `image_urls` に同期します。詳細は `doc/02_DD/03_フロントエンドロジック.md` 33章、テストは `doc/04_TEST/07_テストケース一覧.md` FE-AQ-11〜13 を参照してください。
- API のデータ型・送信用型と商品カテゴリ定数を `frontend/src/lib/apiTypes.ts` に分けました。`api.ts` は既存画面が使う型の再 export と API 呼び出し窓口を引き続き担当します。この分離で API の形や通信動作は変えていません。詳細は `doc/02_DD/03_フロントエンドロジック.md` 34章を参照してください。
- `PriceCalc.tsx` の登録リスト表示を `PriceCalcEntriesList.tsx` に切り出しました。API呼び出し、削除確認・state更新、絞り込みは親に残しています。単体テスト FE-CK-87〜89 と既存の一覧回帰テストを実行し、型チェック・build、Playwright 24件も成功しました。詳細は同設計書35章を参照してください。
- `Checkout.tsx` の注文サマリー表示を `CheckoutOrderSummary.tsx` に切り出しました。state・金額計算・送料取得・注文処理は親に残しています。FE-CM 4件と E2E-Q-05 を含む検証で Vitest 35件・Playwright 6件が成功し、型チェック・build も成功しました。詳細は `doc/02_DD/01_モジュール構成.md` を参照してください。

継続範囲は、今回の注文サマリー以外の大きな画面コンポーネントの分割です。画面ごとの重複した通信・変換処理を減らす API 呼び出し窓口の整理も、現行仕様と実装を調べたうえで別途検討します。既存テストや画面/API仕様を確認し、次の順で進めます。

1. 複数箇所にある同じ処理を調べ、挙動が一致するものから共通helperへ移す。
2. API の型定義と呼び出し窓口を整理する（型定義の配置分離は完了。呼び出し窓口の整理は未着手）。
3. 大きな画面コンポーネントを、表示・入力・データ処理の責務が追える単位に分ける。

**リスク:** 共通化で既存画面の例外的な挙動を失うこと、API型の変更が複数画面に波及すること、画面分割でstateや読み込み順が変わること。

**完了条件:** 変更した画面・APIの関連テストが成功し、画面遷移、入力、保存、エラー表示が変更前と同じ仕様であること。各段階の変更内容を詳細設計とテストケース一覧へ反映すること。

## 5. 第3・第4段階 — バックエンドの分離

第3段階は進行中、第4段階は未着手です。SEOなど独立性を確認しやすい処理から境界を作り、その後に失敗時の挙動が重要な業務処理へ進みます。

### 5-1. SEO等の分離準備

**今回完了した範囲:** sitemap の URL 要素・本文生成を `backend/app/routes/seo_sitemap.py` の `sitemap_url()`・`build_sitemap()` へ分離しました。依存する固定ページ、DB クライアント、行変換、URL生成、ログ処理は引数で渡しています。`seo.py` は sitemap のルート登録、ホスト別判定、キャッシュと失敗時の再生成制御を保持し、既存の内部呼び出し向け `_sitemap_url()`・`_build_sitemap()` wrapper も維持しています。この責務分離で API・SEO の出力仕様は変えていません。詳細は `doc/02_DD/04_バックエンドロジック.md` 14章を参照してください。

- `seo.py` の headタグ生成・HTML挿入と JSON-LD script の安全化を、純粋な文字列処理を行う `backend/app/routes/seo_html.py` に分離しました。互換性のため旧関数名を `seo.py` から再 export しています。`backend/tests/test_seo.py` の143件が成功しました。詳細は `doc/02_DD/04_バックエンドロジック.md` 17章を参照してください。
- SEO 説明文・イベント日付変換・Event / Organization JSON-LD の生成を、FastAPI・DB に依存しない `backend/app/routes/seo_structured_data.py` に分離しました。`seo.py` の既存 wrapper と呼び出し境界を維持し、Event JSON-LD には `PageMeta.description`・`PageMeta.url` を引数で渡します。新規純関数テスト28件と、`test_seo.py` の既存SEO統合143件＋旧定数互換13件の計184件、TypeScript型チェック、本番build、runner回帰3件が成功しました。詳細は `doc/02_DD/04_バックエンドロジック.md` 18章を参照してください。

**未着手の範囲:** `PageMeta` に対応するメタデータ決定、`render_spa_index()` によるHTML全体への適用・ブランド別のPWA処理、robots.txt の処理、`main.py` のルーター登録・ホスト転送・静的配信は今回の分離対象に含めていません。既存のルート・キャッシュの配置も `seo.py` に残しています。これらは出力互換を確認しながら別の変更として検討します。

**リスク:** canonical URL、OGP、サイトマップ、ホスト別ルーティング、キャッシュの挙動が変わる可能性があります。

**完了条件:** 既存のURLとHTML出力を保ち、canonical・OGP・JSON-LD・robots・サイトマップの関連テストを通過すること。実装に合わせて設計書を更新すること。

### 5-2. 予約・イベント・注文の失敗経路テストと分割

分割前に、少なくとも次の失敗経路をテストで確認します。

| 対象 | 分割前に確認する失敗経路 |
|---|---|
| 予約 | 保存失敗、同時予約・定員超過、キャンセル失敗、確認メール送信失敗、Webhook処理失敗 |
| イベント | 保存・更新・削除失敗、関連セッションや画像の更新失敗、権限エラー |
| 注文 | 決済失敗、在庫の一部確保失敗、在庫戻し失敗、注文保存・通知失敗、重複リクエスト |

失敗時の現行仕様をテストで固定した後、`reserve.py`、`events.py`、`orders.py` の責務を一つずつ分離します。一度に複数ドメインを変更しません。

**リスク:** DB更新、在庫、決済、メールの順序やロールバックが変わり、二重予約・二重注文・在庫不整合につながる可能性があります。

**完了条件:** 対象の失敗経路テストと正常系テストが成功し、トランザクション・ロールバック・冪等性・権限の仕様が維持されること。変更後に設計書とテストケース一覧を更新すること。
