# PM-05 — エージェント設計書 (Agent Architecture)

本プロジェクトでは Claude Code のマルチエージェント機能を使い、開発作業を役割ごとの担当（エージェント）に分けて進める。体制と作業の流れの正本はリポジトリ直下の `CLAUDE.md` で、この資料はその内容を設計書としてまとめたもの。担当の定義ファイルは `.claude/agents/` にある。

---

## 1. 全体構成図

```
ユーザー
  |
  v
[PM]（メインのセッション）
  |
  ├─► [frontend] / [backend]   実装（両方必要なら API の形を先に決めて並行）
  |
  ├─► [test-engineer]          テストの追加・関連するテストの実行（失敗は実装担当へ戻す）
  |
  ├─► [qa]                     コードレビュー・デグレ確認（問題は実装担当へ戻す）
  |
  ├─► [docs]                   設計書・テストケース一覧の更新（機能を変えたら毎回）
  |
  ├─► [docs-reviewer]          プッシュ前の設計書の確認（問題は docs へ戻す）
  |
  └─► PM 自身                  関連するテストが ✅ か確認 → ビルド → コミット → main にプッシュ
```

---

## 2. エージェント一覧

| 担当 | 役割 | 直してよいもの | コミット・プッシュ |
|---|---|---|---|
| PM（メインのセッション） | 依頼の整理・仕様決定・担当への指示・結果確認・ユーザーへの報告・コミットとプッシュ | すべて（小さな修正は自分で直してよい） | する（PM だけ） |
| `frontend` | 画面・CSS の実装・修正 | `frontend/src` | しない |
| `backend` | API・DB の実装・修正 | `backend/app/` | しない |
| `test-engineer` | 自動テストの追加と、変えたものに関連するテストの実行 | テストのファイルだけ（`frontend/src/**/__tests__/`・`frontend/e2e/`・`backend/tests/`） | しない |
| `qa` | 実装後のコードレビューとデグレ確認 | 直さない（報告だけ） | しない |
| `docs` | 設計書（`doc/`）とテストケース一覧の更新 | `doc/` | しない |
| `docs-reviewer` | プッシュ前の設計書の確認（管理画面での表示・文章の正確さ） | 直さない（報告だけ） | しない |

`.claude/agents/` には `pm.md`・`deploy.md` の定義ファイルも残っているが、今の体制（`CLAUDE.md`）では PM はメインのセッションが務め、コミット・プッシュも PM が行う。

## 3. 各エージェントの責務

### 3.1 PM

- 依頼を仕様に落とす。決められないことだけユーザーに聞く
- 担当に仕様を渡し、結果を確認してまとめる
- 小さな修正（1〜2ファイル・数行）は担当に振らず自分で直してよい。その場合もテスト・記録・レビューの手順は省かない
- 最後に、最後の変更のあとに流した関連するテストが ✅ かを確かめる（まだなら関連するテストを流す。全体に関わる変更なら全部） → フロントのビルド → コミット → `main` にプッシュ（下の「プッシュしてよい条件」を満たすときだけ）

### 3.2 frontend

- `frontend/src` の画面・CSS を実装・修正する
- コミット・プッシュはしない

### 3.3 backend

- `backend/app/` の API・DB を実装・修正する
- Supabase のテーブルを変える必要があるときは SQL を用意し、人が Supabase の画面で実行する
- コミット・プッシュはしない

### 3.4 test-engineer

- 変えた動作を確かめるテストを追加し、変えたものに関連するテストを実行して、流したファイルと結果を報告する（全部を流すのは全体に関わる変更のときだけ）
- アプリのコード（`frontend/src`・`backend/app`）は直さない。失敗があれば実装担当に戻す

### 3.5 qa

- 仕様と変更内容の突き合わせ、安全面・テストの網羅性の確認を行い、問題を報告する。テストは test-engineer が流すので原則として流さず、確かめたいときだけ関連するテストを記録を残さない `--no-log` で流す
- コードは直さない

### 3.6 docs

- 機能を変えたら毎回、設計書（`doc/`）を更新する
- テストを追加・変更・削除したら `doc/04_TEST/07_テストケース一覧.md` を更新する
- 担当の構成やテストの手順が変わったら本ファイルも更新する

### 3.7 docs-reviewer

- プッシュの前に毎回、更新された設計書を確かめる（誤字・実際の動作との食い違い・日付・表の列数・コードブロックの閉じ忘れなど）
- 直さずに報告する。問題があれば PM が docs に戻す

## 4. テストの手順

テストは `scripts/run_tests.py` で実行する。結果は `doc/04_TEST/08_テスト実行ログ.md` に自動で追加され、1つでも失敗があれば終了コード 1（コミットしてはいけない合図）になる。

**流すのは、変えたものに関連するテストだけ**（2026-10-25 から。すべては流さない）。どれを流すかは次の表で選ぶ（`CLAUDE.md` の「どのテストを流すか」と同じ）。迷ったら広めに選び、何を流したかは報告に書く。

| 変えたもの | 流すテスト |
|---|---|
| 1つの画面・機能の中だけ（例: 販売価格計算の計算式） | その機能のテスト＋その画面の E2E ＋型チェック・ビルド |
| 共通の部品（`api.ts`・MSW のモック・共通コンポーネントなど） | その部品を使う画面のテストまで広げる |
| バックエンドの API | その API の pytest ＋それを呼ぶ画面のテスト |
| 認証・ルーティング・ビルドの設定など、全体に関わるもの | 全部 |

```bash
# 関連するテストだけ（--vitest・--e2e は frontend/ から、--pytest は backend/ から見たパス）
python scripts/run_tests.py --note "何を変えたか" \
  --vitest src/lib/__tests__/priceCalc.test.ts src/pages/admin/__tests__/PriceCalc.test.tsx \
  --e2e e2e/admin-unsaved-pages.spec.ts \
  --pytest tests/test_price_calc_entries.py

# 全体に関わる変更のときだけ、何も絞らずに全部
python scripts/run_tests.py --note "何を変えたか"
```

- どれか1つでも絞ると、指定しなかったテストは流さない（ログには「省略（関連なし）」、見出しは「関連する部分だけ実行」と残り、流したファイルも残る）。型チェックと本番ビルドは、絞った実行でも必ず流す
- 何も絞らなければ、下の6種類をすべて流す

全部を流すときは、次の6種類を順に実行する（2026-10-21 に本番ビルドの確認を追加）。

| 順 | テスト | コマンド |
|---|---|---|
| 1 | TypeScript チェック（型エラーがないか） | `cd frontend && npx tsc --noEmit -p tsconfig.app.json` |
| 2 | 本番ビルド（tsc -b ＋ vite build。一時フォルダに出力し、開発用のダミートークンが残っていないことも確かめる） | `cd frontend && npx tsc -b` → `npx vite build --outDir <一時フォルダ> --emptyOutDir` |
| 3 | フロントのロジック（Vitest） | `cd frontend && npx vitest run` |
| 4 | 画面テスト（Playwright。API は MSW モック） | `cd frontend && npx playwright test` |
| 5 | バックエンド（pytest） | `cd backend && python -m pytest` |
| 6 | 分析ダッシュボード（pytest） | `cd analytics && .venv/bin/python -m pytest tests`（`analytics/.venv` が無い環境ではスキップと記録する） |

- 自動テストは本番につながらない（Supabase は MSW・モックで代わりにする。外部への接続はしない）
- Playwright は `npm run mock:e2e`（`VITE_MSW=true VITE_SKIP_ADMIN_AUTH=true`）を自動で起動する。管理画面はログインを省略し、認証つき API はダミーのトークンで MSW のモックまで届く（2026-10-20 から。本番ビルドでは働かない）
- バックエンドのモックは `patch('app.routes.<module>.supabase', mock_sb)` のようにルートのファイル側に当てる。`app.db.supabase` に当てても効かない（ルートが読み込み時に自分の参照を持つため）
- フロントを変えたら `cd frontend && npm run build` が通ること

## 5. ワークフロー

### 5.1 作業の流れ（機能追加・バグ修正とも）

```
1. PM: 依頼を仕様に落とす（決められないことだけユーザーに聞く）
2. 実装: frontend / backend に仕様を渡す
3. テスト: test-engineer がテストを追加し、関連するテストを実行（失敗は実装担当へ）
4. レビュー: qa がコードレビューとデグレ確認（問題は実装担当へ）
5. 記録: docs が設計書・テストケース一覧を更新（機能を変えたら毎回必ず）
6. 設計書の確認: docs-reviewer が確認（問題は docs へ戻し、もう一度確認）
7. 仕上げ（PM）: 最後の変更のあとに流した関連するテストが ✅ か確かめる（全体に関わる変更なら全部） → frontend/dist/ と doc/ を含めてコミット → main にプッシュ
```

### 5.2 プッシュしてよい条件

次の3つがすべてそろったときだけプッシュする。どれかが欠けていたらプッシュしない。

- 設計書が更新済み
- `docs-reviewer` の確認で問題なし
- 最後の変更のあとに流した `scripts/run_tests.py`（関連するテスト。全体に関わる変更なら全部）が ✅

## 6. 注意事項・制約

| 項目 | 内容 |
|---|---|
| 言葉 | チャットの出力・担当への指示・報告はすべて日本語 |
| シークレット | 秘密の値は `.env` から読む。`.env`・`secret_key.json` は絶対にコミットしない。`SUPABASE_SERVICE_ROLE_KEY` はログにも出さない |
| 絵文字 | コード・コミットメッセージ・設計書のどこにも使わない |
| 同じ作業フォルダ | 担当は同時に同じフォルダで作業することがある。`git stash`・`git reset`・`git checkout -- ファイル`・`git clean` など、コミットしていない変更を退避・取り消す操作は担当は行わない。比べたいときは `git diff` や `git show HEAD:ファイル` を使う |
| コメント | すべてのソースに日本語で詳しいコメントを書く |
| DB 変更 | `backend` は SQL を用意するだけ。人が Supabase の SQL エディターで実行する |
| コミットメッセージ | 末尾に `Co-Authored-By: Claude Sonnet 4.6 <noreply@anthropic.com>` を付ける |
