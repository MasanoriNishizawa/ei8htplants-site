# PM-05 — エージェント設計書 (Agent Architecture)

本プロジェクトでは Claude Code の Agent SDK を用いて、開発作業を役割ごとに分担した複数エージェントで自動化する。

---

## 1. 全体構成図

```
Human
  |
  v
[pm] ─────── 並行スポーン ──────────┐
  |                                  |
  ├─► [frontend]          [backend] ─┤
  |       |                   |      |
  |       └─────── 完了報告 ──┘      |
  |                                  |
  ├─► [qa] (変更検証・テスト実行)     |
  |       |                          |
  |       └─── PASS/FAIL を pm へ    |
  |                                  |
  ├─── Human approval checkpoint ────┘
  |         (はい/yes で次へ)
  |
  ├─► [deploy] (build → commit → push)
  |
  └─► [docs] (設計書更新)
```

---

## 2. エージェント一覧

| エージェント | 役割 | ツール | 起動トリガー |
|---|---|---|---|
| `pm` | オーケストレーター。要件受付・サブタスク分解・承認管理 | Bash, Read, Write, Edit, TodoWrite, **Agent** | ユーザーからの機能追加・バグ修正依頼 |
| `frontend` | フロントエンド実装（React/TypeScript/Vite） | Bash, Read, Write, Edit, TodoWrite | pm から指示 |
| `backend` | バックエンド実装（FastAPI/Python）・DB設計 | Bash, Read, Write, Edit, TodoWrite | pm から指示 |
| `qa` | 型チェック・テスト実行・コードレビュー | Bash, Read, Write, Edit, TodoWrite | pm から指示（frontend/backend 完了後） |
| `deploy` | ビルド・コミット・プッシュ | Bash, Read, TodoWrite | pm から指示（Human 承認後のみ） |
| `docs` | 設計書（本 `doc/` ディレクトリ）の更新 | Bash, Read, Write, Edit, TodoWrite, Artifact | pm から指示（エージェント構成・テスト変更時） |

---

## 3. 各エージェントの責務

### 3.1 pm (Project Manager)

- ユーザーの依頼を受けてサブタスクに分解する
- `frontend` と `backend` の変更が独立している場合は並行スポーン
- 全エージェントの結果を集約し、変更内容・テスト結果・デプロイ計画を Human に提示
- **Human 承認を受けるまで `deploy` を呼ばない**
- `deploy` 完了後に `docs` を呼ぶ（エージェント定義またはテストに変更があった場合）

### 3.2 frontend (Frontend Developer)

- `frontend/src/` 配下のファイルのみ変更する
- ビルドやコミットは行わない（deploy の責務）
- 新しいロジック関数を追加したら、テストケースの追加も行う

### 3.3 backend (Backend Developer)

- `backend/app/` 配下の実装を担当
- Supabase スキーマ変更が必要な場合は SQL を出力し、Human に手動実行を求める
- 新しい API エンドポイントを追加したら、pytest テストも追加する

### 3.4 qa (QA / Testing)

実行チェックリスト（必ず以下の順で実施）:

1. TypeScript 型チェック:
   ```bash
   cd frontend && npx tsc --noEmit
   ```
2. フロントエンド UT / IT（Vitest）:
   ```bash
   cd frontend && npx vitest run
   ```
3. バックエンド UT / IT（pytest）:
   ```bash
   cd backend && python -m pytest
   ```
4. E2E システムテスト（Playwright — ST 層）:
   ```bash
   cd frontend && npx playwright test
   ```
   Playwright は `npm run mock`（MSW モード）を自動起動する。本番 DB への接続なし。
   ページのレンダリング・ルーティング・ユーザーフローに影響する変更の後に必ず実行する。
5. コードレビュー（ロジック・セキュリティ・i18n・型定義の整合性）

**重要**: バックエンドのモックは必ず `patch('app.routes.<module>.supabase', mock_sb)` でルートレベルにパッチする。`app.db.supabase` へのパッチは効果がない（ルートがモジュールロード時にローカル参照を持つため）。

### 3.5 deploy (Deployer)

- `npm run build` でフロントエンドをビルド
- 変更ファイルを `git add` → `git commit` → `git push`
- コミットメッセージ末尾に必ず付与:
  ```
  Co-Authored-By: Claude Sonnet 4.6 <noreply@anthropic.com>
  ```
- Human 承認なしには絶対に実行しない

### 3.6 docs (Documentation Writer)

- `doc/` 配下の設計書ファイルを更新・作成する
- エージェント定義（`.claude/agents/*.md`）が変更された場合: 本ファイルを更新
- テストファイル（`frontend/src/**/*.test.ts`, `backend/tests/*.py`）が変更された場合: テストケース一覧を更新

## 4. ワークフロー詳細

### 4.1 通常の機能追加フロー

```
1. Human → pm: 機能追加の依頼
2. pm → frontend + backend: 並行スポーン（独立タスクの場合）
3. frontend / backend → pm: 実装完了を報告
4. pm → qa: 変更の検証を依頼
5. qa → pm: PASS / FAIL を報告
6. pm → Human: 変更内容・テスト結果・デプロイ計画を提示
7. Human: "はい" / "yes" で承認
8. pm → deploy: ビルド・コミット・プッシュ
9. pm → docs: 設計書更新（必要な場合）
```

### 4.2 バグ修正フロー

```
1. Human → pm: バグ報告
2. pm → frontend または backend: 修正を依頼
3. pm → qa: 修正の検証 + リグレッションテスト
4. (以降は機能追加フローと同じ)
```

---

## 5. 注意事項・制約

| 項目 | 内容 |
|---|---|
| シークレット | `.env`, `secret_key.json` は絶対にコミットしない |
| 絵文字 | コード・コミットメッセージ・設計書のどこにも使わない |
| DB 変更 | `backend` エージェントは SQL を出力するのみ。Human が Supabase SQL エディターで実行する |
| 承認スコープ | Human の承認は1タスクに対してのみ有効。次のタスクで再承認が必要 |
