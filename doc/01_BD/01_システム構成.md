# BD-01 — システム構成 (System Architecture)

## 1. アーキテクチャ概要

```
ブラウザ (React SPA)
    │
    │  /api/* → HTTP
    │
    ├── [開発時] Vite dev server (port 5173)
    │               │ proxy /api → localhost:8000
    │               ▼
    └── [本番時] ─── FastAPI (uvicorn, port 8000)
                         │
                         ├── Supabase (PostgreSQL + Auth + RLS)
                         │       ← データ読み書き・管理者認証
                         │
                         ├── Resend API
                         │       ← メール送信（お問い合わせ・予約・注文・発送・返信）
                         │
                         ├── Square Payments API
                         │       ← カード決済（/checkout の注文確定時）
                         │
                         └── Gemini API（Google）
                                 ← AI チャットの回答作り（/chat）
```

**開発時**: Vite dev server + uvicorn の2プロセス構成。Vite の proxy 設定で `/api` をバックエンドに転送。  
**本番時**: `npm run build` でビルドしたSPAを FastAPI の `StaticFiles` で配信。単一プロセス。

### 3ブランドのドメインと表示先（2026-10-26 追加）

本番では、3つのブランドを**同じRender Web Service・同じリポジトリ**から配信する。アクセスしたドメイン名をフロントエンドが判定し、表示するサイトと共通部品（ヘッダー・フッター）を選ぶ。ドメインごとに別のサーバーやデータベースを用意する構成ではない。

| ドメイン | 表示するサイト | 主な画面・用途 |
|---|---|---|
| `ei8htplants.com` | ei8ht plants | 既存サイト、ショップ、ジャーナル、管理画面 |
| `habitatoides.com` | Habitat Oides | 独自の内容・写真・配色・レイアウトのホーム、ワークショップ、コラボレーション |
| `huebyei8htplants.com` | HUE by ei8ht plants | 独自の内容・ビジュアル・レイアウトのホーム |

独立ブランドは共通テーマで色だけを変える構成ではなく、それぞれ専用のホームページとヘッダー・フッターを持つ。各ブランドのヘッダー・フッターとei8ht plants側のブランド切替リンクは、新しいタブで開く。各ドメインの `www` 付きアドレスも同じサイトとして扱う。Render の設定では `www` から各ブランドのルートドメインへ転送する。独立ブランド側の `/admin` は管理画面を持たず、既存の `https://ei8htplants.com` の同じパスへ移動する。

旧サイトのブランドページ URL は、検索エンジンや保存済みリンクから来た人を新しい正式 URL へ301転送する。`/habitatoides` と `/habitatoides/workshop` は Habitat Oides ドメインへ、`/hue` は HUE ドメインへ、`/collaborations` は Habitat Oides ドメインへ転送する。さらに `habitatoides.com/hue` は HUE ドメインへ、`huebyei8htplants.com/habitatoides` は Habitat Oides ドメインへ転送する。`habitatoides.com/hue` をページ内から開いた場合もアプリがHUEドメインへ案内する。実装は `frontend/src/lib/siteHost.ts`・`frontend/src/sites/`・`backend/app/main.py` を参照。詳しくは [FT-27 ブランド別ドメインとサイト表示](features/16_ブランド別ドメインとサイト表示.md)。

独立ブランドドメインでは、過去に保存されたPWAのService Workerとキャッシュを解除してから最新のサイトを再表示し、以後そのドメインでPWAキャッシュを作成しない。ei8htplants.comのPWAには影響しない。

### 検索エンジン・SNS 向けの情報（2026-10-21 追加、2026-10-26 更新）

公開サイトは、ブラウザで JavaScript が動いてから画面を作る仕組み（SPA）になっている。LINE・X・Facebook などがリンクのプレビュー（タイトル・説明・画像のカード）を作るときは JavaScript を動かさないため、これまではどのページを共有してもサイト共通の情報しか出なかった。

2026-10-21 から、サーバーがページの入口（`index.html`）を返すときに、開かれた URL に合わせて次の情報を入れてから返す（`backend/app/routes/seo.py`）。

- ページのタイトル・説明文
- 正式な URL（canonical。同じページに複数の URL があるとき、検索エンジンにどれを使うかを伝える）
- SNS のプレビュー用の情報（OGP・X のカード。タイトル・説明・画像）
- 検索結果に出さない印（noindex。管理画面・予約キャンセル・購入手続き、存在しないページ）
- 構造化データ（Google にページの中身を機械が読める形で伝える情報。イベントのページはイベントの日時・会場、トップページはお店の名前・ロゴ）

あわせて、検索エンジン向けに `robots.txt`（読み取ってよい範囲の案内）と `sitemap.xml`（公開ページの一覧）を返す。3ブランドの独立ドメインでは、ドメインごとにブランド名・正式URL・掲載ページを切り替える。詳しくは [FT-26 検索エンジン・SNS 向けの情報](features/15_検索エンジン・SNS向け情報.md) を参照。

### 表示の速さ — 画面ごとの読み込み（2026-10-21 追加）

これまでは、どのページを開いても公開サイトと管理画面の全部のプログラム（約 910KB、通信時の圧縮後で約 246KB）を最初に読み込んでいた。2026-10-21 から、トップページと全ページ共通の部品だけを最初に読み込み、ほかのページはそのページを開いたときに読み込む（最初の読み込みは約 298KB、圧縮後で約 93KB）。

- 公開サイトを見る人は、管理画面のプログラムを読み込まない
- ログイン用の Supabase のプログラム（約 200KB）は、ログインが必要な操作のときに初めて読み込む
- 管理画面は、ログインして画面が出たあと、手が空いたときに残りの管理ページをまとめて先に読み込む（メニューで移動するときに待たない）
- 新しい版を公開すると古いファイルは消える。公開前から開いていた画面で別のページへ移って読み込みに失敗したときは、自動で1回だけ再読み込みする。それでも失敗したら「ページを読み込めませんでした。再読み込みしてください。」と「再読み込み」ボタンを出す
- スマホのホーム画面に追加したアプリ（PWA）は、分けたファイルも含めて先に取り込んでおく
- ただし、独立ブランドドメインはei8ht plants用のPWAとして動作しない。ブランドを分ける前のService Workerや保存キャッシュが残っている場合は、サーバーとページ内の処理で登録・キャッシュを解除し、ページを読み直す

### 分析ダッシュボード（2026-10-17 追加）

サイト本体とは別に、売上・収支・予約などをグラフで見るための「分析ダッシュボード」を **Streamlit Community Cloud**（Streamlit の無料の公開サービス）で動かしている。管理画面の左のメニュー「分析 ↗」を押すと、新しいタブで開く。

はじめは Render の別のサービスとして動かしていたが、Render の無料枠（すべてのサービスを合わせて月 750 時間まで動かせる）をサイト本体と分け合うと足りなくなったため、2026-10-17 に Community Cloud へ移した。Render ではサイト本体だけを動かす。

```
ブラウザ（管理画面のメニュー「分析 ↗」から新しいタブで開く）
    │
    │  https://ei8htplants-analytics.streamlit.app
    ▼
分析ダッシュボード（Streamlit。Streamlit Community Cloud。analytics/ フォルダ）
    │
    ├── Supabase Auth
    │       ← ログイン（管理画面と同じメールアドレス・パスワード）
    │
    ├── Supabase（PostgreSQL）
    │       ← データの読み取りだけ（書き込み・削除はしない）
    │
    └── Google アナリティクス 4（任意）
            ← アクセス数の読み取りだけ（アクセス解析の画面）
```

- サイト本体とは別の場所で動いているので、分析ダッシュボードが止まってもサイト・管理画面には影響しない
- しばらく使われないと休止し、次に開いたときは起動を待つ（無料の公開サービスの仕様）
- 画面・ログイン・データの扱いは [FT-25 分析ダッシュボード](features/14_分析ダッシュボード.md)、公開の手順は [OP-04 分析ダッシュボードの公開手順](../05_OP/04_分析ダッシュボードの公開手順.md) を参照

### 分析ダッシュボード（2026-10-17 追加）

ローカルではリポジトリ直下の `.env` から読む。公開先の Community Cloud では、アプリの設定の **Secrets** に TOML という形式（`名前 = "値"`）で一番外側に書く。一番外側に書いた値は、プログラムからは環境変数として読める（値は設計書に書かない）。

| 変数名 | 必須 | 公開 | 説明 |
|---|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | 必須 | 非公開 | Supabase プロジェクトURL（ログインとデータの読み取り） |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | 必須 | 非公開 | 匿名キー。ログイン（Supabase Auth）だけに使う |
| `SUPABASE_SERVICE_ROLE_KEY` | 必須 | **絶対に非公開** | データの読み取り（GET だけ）に使う。ログインには使わない |
| `ANALYTICS_ALLOWED_EMAILS` | 推奨（実質必須） | 非公開 | 見てよい人のメールアドレス（カンマ区切り、大文字小文字は区別しない）。未設定なら Supabase にログインできる人は全員見られる。Supabase で新規登録ができる設定だと、第三者が登録して見られてしまうため、必ず設定する |
| `GA_PROPERTY_ID` | 任意 | 非公開 | GA4 のプロパティ ID（数字。測定 ID の `G-…` ではない） |
| `GA_CREDENTIALS_JSON` | 任意 | **絶対に非公開** | GA4 の読み取り用の鍵ファイルの**中身**（JSON）。Community Cloud には鍵ファイルを置けないため、こちらを使う。Secrets では `'''` で前後を囲んで貼る。`GA_CREDENTIALS` と両方あればこちらを使う |
| `GA_CREDENTIALS` | 任意 | 非公開 | GA4 の読み取り用の鍵ファイルの場所（自分の PC で動かすとき向け。鍵ファイルはリポジトリの外に置く） |

> **重要**: `.env` ファイルは `.gitignore` で管理。リポジトリに絶対にコミットしないこと。

## 5. デプロイ手順（概要）

本番は Render で動いている。`main` ブランチにプッシュすると、Render が自動で新しい版を作り直して公開する（手でサーバーを起動する作業はない。2026-10-22 に記述を今のやり方に合わせた）。

```
1. フロントエンドをビルドする
   cd frontend && npm run build
   → frontend/dist/ にできたファイルもコミットする（Render はこのフォルダをそのまま配信する）

2. 変えたものに関連するテストを流す（最後の変更のあとに流したものが ✅ ならよい）
   python scripts/run_tests.py --note "何を変えたか" --vitest <関連するファイル> --e2e <関連するファイル> --pytest <関連するファイル>
   （全体に関わる変更のときだけ、何も絞らずに python scripts/run_tests.py --note "何を変えたか"）

3. main ブランチにプッシュする
   → Render が自動で反映する

4. DB の変更があるとき（そのときだけ）
   Supabase の SQL エディタで backend/migrations/ の新しいファイルを実行する
   （順番と注意は DD-05 データベース詳細の「マイグレーション管理」を参照）
```

## 6. 管理者認証フロー

```
/admin アクセス
    │
    └── AdminLayout: supabase.auth.getSession() 実行
            │
            ├── session あり → Admin UI 表示
            └── session なし → ログインフォーム表示
                                    │
                    メール + パスワード入力
                                    │
                supabase.auth.signInWithPassword()
                                    │
                    ├── 成功 → セッション確立 → Admin UI
                    └── 失敗 → エラーメッセージ表示

バックエンドAPI（Admin操作）:
    フロント（lib/api.ts）が Authorization: Bearer <Supabase のログインのトークン（JWT）> を付けて送る
        │
        ▼
    backend/app/auth.py の require_auth（管理画面用の API に Depends で付ける）
        ├─ Authorization が無い・"Bearer " で始まらない → 401
        ├─ supabase.auth.get_user(トークン) でユーザーを確かめる
        │     ├─ ユーザーあり → API の処理へ
        │     └─ ユーザーなし・確認中のエラー → 401
        ▼
    API の処理: SUPABASE_SERVICE_ROLE_KEY で作った admin_supabase で読み書き（RLS バイパス）
```

管理画面用の API（`(auth)` の付いたもの。例: 管理情報・収支・お問い合わせ一覧・2026-10-21 追加のダッシュボード用 API）は、ログインしていないと 401 になる。公開ページ用の API（イベント一覧など）は認証なしで使える。トークンの決め方は [DD-06 API仕様](../02_DD/06_API仕様.md) の「`(auth)` の付いた呼び出しで送るトークン」を参照（2026-10-21 に記述を今の実装に合わせた。それまでは「リクエスト認証は未実装」と書いていた）。

分析ダッシュボードのログイン（2026-10-17 追加）は、管理画面と同じアカウントを使うが、管理画面のログイン状態は引き継がない（別の場所で動いているため、開いたら改めてログインする）。詳しくは [FT-25 分析ダッシュボード](features/14_分析ダッシュボード.md) の「ログイン」を参照。
