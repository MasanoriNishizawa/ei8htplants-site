# FT-25 — 分析ダッシュボード

（2026-10-17 追加。同日、公開先を Render から Streamlit Community Cloud に変更）

## 概要

イベントの収支・ワークショップの予約・ショップの注文・問い合わせ・サイトのアクセス数を、グラフと表でまとめて見るための画面。サイト本体とは別のプログラム（`analytics/` フォルダ。Streamlit という Python の画面作成の仕組みを使う）で、Streamlit Community Cloud（Streamlit の無料の公開サービス）で公開している。はじめは Render の別のサービスとして公開していたが、Render の無料枠（すべてのサービスを合わせて月 750 時間まで動かせる）をサイト本体と分け合うと足りなくなったため移した。

- 開き方: 管理画面の左のメニュー「分析 ↗」を押す（新しいタブで `https://ei8htplants-analytics.streamlit.app` が開く）
- 見られる人: 管理画面と同じメールアドレス・パスワードでログインでき、見てよい人のリスト（`ANALYTICS_ALLOWED_EMAILS`）に入っている人（下の「ログイン」を参照）
- データ: 本番の Supabase のデータを**読むだけ**。ここから内容を書き換えたり消したりすることはできない
- しばらく使われないと休止する（無料の公開サービスの仕様）。休止中に開くと起動を待つ必要があり、起こすためのボタン（「Yes, get this app back up!」など）が出たときは押す

## 予測・シミュレーション: 今期のイベント売上の着地見込み

（2026-10-19 更新: 同じイベントの過去の売上と、開催時期の近さを考慮するようにした）

今期（4月〜翌3月）のイベント売上が、年度末にいくらぐらいになりそうかを見込む。売上の入力されたイベントが 5 回未満のときは表示しない。

### 計算のしかた

1. 今期すでに売上が入っているイベントの合計を「ここまでの実績」とする
2. 今期のイベントのうち、まだ売上が入っていない回（今後の予定と、開催したが売上の入力待ちの回）を「残りのイベント」とする
3. 残りのイベント1回ごとに、売上を「くじ」で引いて足す。これを 5,000 回くり返し、合計がどのぐらいに散らばるかを見る（ブートストラップ法: 過去の実績をくじに見立てて何度も引き直し、ありそうな結果の幅を見る方法）
4. 5,000 回の結果を小さい順に並べ、下から 10% の位置を「控えめな見込み」、真ん中を「ふつうの見込み（中央値）」、上から 10% の位置を「良い見込み」として表示する

1回分のくじは、次の2種類のどちらかから引く。

| くじ | 中身 | 選ばれる割合 |
|---|---|---|
| (1) 同じイベントの過去の売上 | 残りのイベントと同じイベント（下の「同じイベントの見分け方」）の、今日より前に開催して売上が入っている回。開催月が近い回ほど当たりやすい | 下の「同じイベントの重み」 |
| (2) 全イベントの1回あたり売上 | 売上が入っているすべてのイベントの売上（開催時期は考えない） | 残り（100% −「同じイベントの重み」） |

同じイベントの過去の回が1回も無いイベントは、(2) だけから引く（この変更の前と同じ結果になる）。

### 同じイベントの見分け方

イベント名から「回ごとに変わる番号」を取り除き、残った名前が同じなら同じイベントとみなす。取り除いたあとは、空白・記号を消し、全角の英数字を半角に、英字の大文字を小文字にそろえて比べる。

| 取り除くもの | 例 |
|---|---|
| 第N回・N回目・第N回目（漢数字も含む） | 第3回、第三回、第十二回、5回目、第5回目 |
| vol と番号 | vol.5、Vol 12、vol5、volume 2 |
| 英語の序数（単独の言葉になっているもの） | 1st、6th、11th |
| 複数日開催の「何日目」 | day1、Day 2、day.3（「Sunday1」のように言葉の一部になっているものは消さない） |
| # と番号、no. と番号 | #3、no.4、No. 4 |
| 西暦と月（日まで書いたものも） | 2026.4、2025/10、2026-04、2026.4.12、2026年4月、2026年4月12日 |
| 西暦4桁 | 2026、2026年 |
| かっこ内が数字だけのもの | (3)、（12） |

| 元の名前 | まとめるための名前 |
|---|---|
| 奇天烈 vol.5 / 奇天烈 Vol.12 | 奇天烈（同じイベント） |
| 植物と暮らしのマーケット『THE BOTANICAL SHOW 6th』 | 植物と暮らしのマーケットthebotanicalshow |
| Habitat Exhibition 2026 | habitatexhibition |
| 第3回 〇〇 / 第三回 〇〇 | 〇〇（同じイベント） |
| ブース2 / 3Dプリント展 | 数字は名前の一部なので消さない |

- 番号を取り除くと何も残らない・数字だけが残る・英数字だけで2文字未満しか残らない名前（「Vol.1」「Vol.2」「A 2026」など）は、元の名前のまま比べる。別々のイベントが同じ名前にまとまってしまうのを防ぐため。そのため「Vol.1」と「Vol.2」は別のイベントになる
- 日本語は1文字でも名前として使う（「第十二回 祭」→「祭」）
- 名前が空のイベントは、どのイベントとも同じとみなさない

### 開催時期の近さ（時期の重み）

年に何回か開催するイベントは、季節によって売上が違うことがある。そのため、同じイベントの過去の回のうち、残りのイベントと**開催月が近い回ほど重く見る**。年は関係なく月だけで比べ、12月と1月はとなりの月（1か月差）として数える。

| 開催月の差 | 同じ月 | 1か月 | 2か月 | 3か月 | 4か月 | 5か月 | 6か月 |
|---|---|---|---|---|---|---|---|
| 時期の重み | 1.00 | 0.80 | 0.41 | 0.14 | 0.03 | 0.004 | ほぼ 0 |

（計算式は exp(−d² ÷ (2 × 1.5²))。d は開催月の差。1.5 は重みが下がっていく幅（か月）を決める値）

- 開催日が分からない回は、時期で差をつけず重み 1.00 とする
- (1) のくじでは、各回がこの重みに比例して当たりやすくなる

### 同じイベントの重み（(1) から引く割合）

時期の重みを合計したものを「時期を考慮した実質の回数」と呼ぶ（同じ月の回が2回なら 2.0、同じ月の回と3か月ずれた回なら約 1.1）。実質の回数を n として、

**同じイベントの重み ＝ n ÷ (n + 2)**

| 実質の回数 | 1 | 2 | 4 | 8 |
|---|---|---|---|---|
| 同じイベントの重み | 33% | 50% | 67% | 80% |

- 回数が少ないうちは、たまたま良かった（悪かった）1回に引っぱられすぎないよう、全イベントの実績を多めに混ぜる。回数が増えるほど同じイベントの実績を信じる（「2」はその混ぜ具合を決める値）
- 実質の回数が 0.001 未満（開催時期が半年ずれた回しか無いなど）のときは、同じイベントの重みを 0% にして、全イベントの実績だけで見込む

例: 春と秋に開催するマルシェで、過去に4月の回（売上 10万円）と10月の回（売上 30万円）があり、来年4月の回を見込むとき

- 4月の回の時期の重みは 1.00、10月の回はほぼ 0。実質の回数は約 1.0 で、同じイベントの重みは約 33%
- この回の見込みは、約 33% の確率で 10万円（4月の回）、約 67% の確率で全イベントの実績から引く。10月の回の 30万円はほぼ選ばれない

### 画面の表示

| 表示 | 内容 |
|---|---|
| 説明文 | 上の計算のしかた（2種類のくじ、時期の重み、同じイベントの重みの式と例） |
| ここまでの実績 / 控えめな見込み（下位10%） / ふつうの見込み（中央値） / 良い見込み（上位10%） | 4つの金額 |
| 今期の売上合計の分布 | 5,000 回の結果のグラフ（ヒストグラム）。下位10%・中央値・上位10% の位置に点線 |
| 残りのイベントと参考にした実績（表） | 残りのイベント1つにつき1行。開催日の早い順（下の表） |

「残りのイベントと参考にした実績」の表の列:

| 列 | 内容 |
|---|---|
| イベント名 | 残りのイベントの名前（名前が無いときは「（名前なし）」） |
| 開催日 | 年-月-日 |
| 同じイベントの過去の回数 | まとめた過去の回の数 |
| 時期を考慮した実質の回数 | 時期の重みの合計（小数1桁） |
| 過去の売上の中央値 | まとめた過去の回の売上の真ん中の値（時期の重みを付けて数える）。同じイベントの過去の回が無いとき、または同じイベントの重みが 0.5% 未満でほとんど見込みに効いていないときは「なし（全体の実績で見込み）」 |
| 同じイベントの重み | (1) から引く割合（%） |
| まとめた過去の回 | 「名前（YYYY年M月・重み80%）」を開催日順に「 / 」でつないだもの。開催日が分からない回は「時期不明」。ここの重みは時期の重み |

今期の残りのイベントが無いときは、表の代わりに「今期の残りのイベントはありません。」と出る。

### 見込みの精度を上げるために

- 開催したら、管理画面の収支に売上を入れる（売上 0 円の回は「入力前」とみなされ、くじに入らない）
- 今後出店する予定のイベントを登録しておく（登録したイベントだけが「残りのイベント」として数えられる）
- 同じイベントは、回の番号（vol.5・第3回・2026 など）以外の名前をそろえる（例: 「奇天烈 vol.5」と「奇天烈vol.6」はまとまるが、「奇天烈マーケット vol.6」は別のイベントになる）

## ログイン

管理画面と同じ Supabase のアカウントを使う。ただし管理画面とは別の場所で動いているので、管理画面にログインしていても、分析ダッシュボードを開いたら改めてログインする。

| 場面 | 動き |
|---|---|
| 開いたとき | 「ei8ht plants 分析」の見出しと、メールアドレス・パスワードの入力欄、「ログイン」ボタンだけが出る。ログインするまでは、グラフもデータの読み込みも行わない |
| 正しく入力したとき | 分析の画面が表示される。左のメニューに「ログイン中: メールアドレス」と「ログアウト」が出る |
| メールアドレスかパスワードが違うとき | 「メールアドレスまたはパスワードが違います。」 |
| ログインに失敗したとき（どの理由でも） | メールアドレス・パスワードの入力欄は空に戻る（パスワードを画面に残さないため）。もう一度両方を入れる |
| どちらかが空のまま押したとき | 「メールアドレスとパスワードを入力してください。」（失敗の回数には数えない） |
| 見てよい人に入っていないとき | 「このアカウントでは閲覧できません。」（`ANALYTICS_ALLOWED_EMAILS` を設定したときだけ） |
| 5回続けて失敗したとき | 最後の失敗から 60 秒は「ログインの失敗が続いたため、しばらく待ってからもう一度お試しください。」と出て、ログインを試せない。60 秒たてば、回数を数え直してまた試せる |
| 認証のサーバーにつながらないとき | 「認証サーバーに接続できませんでした。時間をおいてもう一度お試しください。」（失敗の回数には数えない） |
| ログインの設定（Supabase の URL・キー）が無いとき | 「ログインの設定がありません（NEXT_PUBLIC_SUPABASE_URL / NEXT_PUBLIC_SUPABASE_ANON_KEY）。」と出て、入力欄も出ない |
| ブラウザを再読み込みしたとき・タブを閉じて開き直したとき | もう一度ログインが必要 |
| 「ログアウト」を押したとき | ログイン画面に戻る |
| ログイン中に、見てよい人のリストから外されたとき | 次に画面を操作したとき（メニューを押す・ボタンを押すなど）にログアウトされ、ログイン画面に戻る。ログインしたあとも、画面を描くたびにリストを確かめ直している |

### 見てよい人を絞る（`ANALYTICS_ALLOWED_EMAILS`。必ず設定する）

Supabase で新規登録ができる設定だと、第三者がアカウントを作って見られてしまうため、必ず設定する（あわせて Supabase の新規登録をオフにする。[OP-04](../../05_OP/04_分析ダッシュボードの公開手順.md) の 2 章）。

- Community Cloud の Secrets の `ANALYTICS_ALLOWED_EMAILS` に、見てよい人のメールアドレスをカンマ区切りで入れる（例: `a@example.com,b@example.com`）
- 大文字・小文字の違いと、前後の空白は無視する。一部だけ一致するメールアドレスは通さない
- 設定しないとき（空のとき）は、Supabase にログインできる人は全員見られる
- リストから外した人は、ログイン中でも、次に画面を操作したときにログアウトされる
- 判定には、入力したメールアドレスではなく、Supabase がログイン成功時に返したメールアドレスを使う

### 守っていること

- パスワードと、ログイン成功時に Supabase から返る合言葉（トークン）は保存しない。画面にも記録（ログ）にも出さない。覚えておくのはメールアドレスだけ
- ログインしたあとは、パスワード欄に入力した値をサーバー側の状態からも消す。ログインに失敗したときも入力欄を空に戻す
- 予期しないエラーが起きても、エラーの詳しい内容（プログラムの場所など）は画面に出さない（内容は Community Cloud の画面右下の **Manage app** で出る記録（ログ）で確かめる）。この設定は設定ファイルに加えて `analytics/app.py` の先頭でも入れていて、設定ファイルが読まれない起動の仕方でも効く
- ログインの確認には公開用のキー（anon キー）を使い、データを読むための強い権限のキー（service_role キー）は使わない
- ログインの失敗の回数は、そのブラウザのタブの中だけで数える。再読み込みすると数え直しになる簡易的な対策で、実際の総当たり対策は Supabase 側の回数制限が担う

## データの扱い

| 項目 | 内容 |
|---|---|
| 読むデータ | イベント・イベント収支・WS の時間枠・WS 予約・商品・注文・注文の明細・問い合わせ・記事 |
| 読まないデータ | 氏名・電話番号・住所・問い合わせの本文（読み込む列をあらかじめ決めていて、これらは含めない） |
| メールアドレス | 予約・注文のメールアドレスは「同じ人か」の判定（リピーターの集計）だけに使う。読み込んだらすぐ別の文字列に置き換え（ハッシュ化）、元のメールアドレスは残さない |
| 書き込み | しない（読み取りだけ。追加・変更・削除の通信は行わない） |
| 読み直しの間隔 | 10 分。左のメニューの「データを再読み込み」で、すぐに読み直せる |
| 読む順番 | 件数が多い表は何回かに分けて読む。分けたときに境目で行が重なったり抜けたりしないよう、必ず重ならない列の順に並べて読む（注文の明細など多くの表は id の順、イベント収支はイベントの id の順。2026-10-23 記載） |
| 収支の計算 | 管理画面の収支（`frontend/src/lib/finance.ts` の `computeFinances`。2026-10-22 に `lib/api.ts` から移した）と同じ計算式（`analytics/lib/finance.py`）。管理画面の式を変えたら、こちらも合わせて直す |
| 売上が 0 円の収支 | 「まだ開催していない・入力前」とみなして集計から外す |
| アクセス解析 | GA4 の数字を読み取りだけの権限で読む。鍵は、公開先では Secrets の `GA_CREDENTIALS_JSON`（鍵ファイルの中身）、自分の PC では `GA_CREDENTIALS`（鍵ファイルの場所）で渡す（両方あれば `GA_CREDENTIALS_JSON` を使う）。`GA_PROPERTY_ID` や鍵が無い・鍵の中身が読めないときは、画面に理由と設定の手順を表示する。鍵の中身は画面にも記録（ログ）にも出さない |
