# TEST-01 — マスターテスト計画書 (Master Test Plan)

## 1. テストの全体方針

本プロジェクトは小規模1人開発のため、正式なテストフェーズを分離せず、実装と並行してテストを実施する。各フェーズのテストの目的と合否基準を本書に定義する。

---

## 2. テストレベルと対応設計書

| テストレベル | 対象 | 対応設計書 | 合否基準 |
|---|---|---|---|
| 単体テスト (UT) | 個別関数・コンポーネント | DD（詳細設計） | 関数が仕様通りの出力を返すこと |
| 結合テスト (IT) | フロントエンド ⇔ バックエンド API 連携 | BD（基本設計） | APIのリクエスト/レスポンスが仕様通りであること |
| システムテスト (ST) | システム全体の機能動作 | RD（機能要件） | 全機能要件を満たすこと |
| 受入テスト (UAT) | 業務フローの観点 | RD（業務要件） | サイトオーナーが実際に操作して問題なく使えること |

---

## 3. テスト環境

| 環境 | 詳細 |
|---|---|
| テスト実施環境 | ローカル開発環境（Vite dev server + uvicorn） |
| DB | 本番 Supabase（開発・本番共通） |
| ブラウザ | Chrome 最新版（主）、Safari 最新版（副） |
| モバイル | Chrome DevTools のデバイスエミュレーション |

> **注意**: テスト時に本番DBへのデータ書き込みを伴うテストケースは、テスト後に手動でデータを削除すること。

---

## 4. テストスケジュール

| フェーズ | タイミング |
|---|---|
| UT / IT | 各機能の実装完了直後 |
| ST | Phase 3（全機能実装）完了後 |
| UAT | 本番デプロイ前（サイトオーナーによる確認） |

## 6. 合否基準（総合）

- 全 ST テストケースが PASS であること
- UAT で致命的な操作不能事象がないこと
- 秘匿情報（`.env`）がリポジトリに含まれていないこと
- 管理者認証が正常に機能すること
